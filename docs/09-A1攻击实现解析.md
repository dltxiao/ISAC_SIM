# A1 感知篡改诱导通信拥塞：代码走读与实现解析

> 代码基线：`master`（`d045fe1`，v0.2.0）。本文只讲 A1，不涉及 A2–A4，也不涉及 feature 分支的 A5–A10。
> 目标：从 Web/CLI 下发 A1 开始，沿着源码走完“选目标 → 伪造目标 → 注入 → ADAS → 制动 → 信道 → 真值 → 检测”，并明确哪些是代码保证的、哪些只是命名或预期。

## 0. 先约定

| 符号 | 含义 |
|---|---|
| `a` | 攻击强度 `amplitude`；`_level()` 会夹到 `[0, 1]`，但幽灵数 `n` 用的是未夹的原始值 |
| `t0` / `t1` | 攻击实际开始 / 计划结束的仿真时刻，`t1 = t0 + duration` |
| tick | 仿真步长，默认 `0.05 s`（[config.py](../isacsim/config.py:64)） |
| 目标 RSU | A1 选中的路侧单元，幽灵目标只注入它的 `sensing.objects` |
| 受害车 | A1 选中的车辆，真值 `params.victim` 记录它；但它不一定被该 RSU 覆盖，也不一定有 ADAS |

---

## 1. 一句话概括

A1 的代码只做三件事：

1. 在**目标 RSU** 的 `sensing.objects` 里追加一批**静止的幽灵目标**；
2. 每个 tick 给 `ctx.extras["v2x_extra_load"]` 加一个**标量负载** `extra_load`；
3. 每 0.5 s 伪造一条 `v2x.denm`（`forged=true`）。

它**不直接调用刹车**，也**不逐包发送 450 msg/s**。

- “感知篡改”是第 1 件事：目标列表里多了不存在的东西；
- “通信拥塞”是第 2 件事：信道模型把 `extra_load` 折算成 CBR/PER/时延；
- “制动”是第 1 件事的**下游后果**：如果受害车有 ADAS 且被目标 RSU 覆盖，ADAS 会把幽灵当成障碍并发出正常的 `control.command`。

这条链的关键在于：**攻击只改输出侧数据，物理制动由系统自己产生**。这也是 A1 与 A2/A3 的区别——A2/A3 会直接调用 `ControlLayer.inject_brake()`，A1 不会。

### 1.1 端到端调用链

```text
Web: POST /api/attacks {type:"A1", amplitude, duration, start, count}
  └─ SessionManager.submit_attack()              web/session.py:92
      └─ Simulation.submit_attack()              core/engine.py:217
          └─ AttackScheduler.submit()            attacks/scheduler.py:25
              └─ CampaignA1(...)                 attacks/campaigns.py:25
                  │
                  ├─ t0: start(ctx)              attacks/campaigns.py:38
                  │   ├─ pick_rsu() / pick_vehicle()
                  │   ├─ 生成 ghosts
                  │   ├─ hooks.on("sensing.objects", hook)
                  │   └─ truth.add(truth())      attacks/scheduler.py:66
                  │
                  └─ 每个 tick: tick(ctx)         attacks/campaigns.py:66
                      ├─ extras["v2x_extra_load"] += extra_load
                      └─ 每 0.5 s emit 伪造 DENM

每个仿真步（core/engine.py:107）：
  sumo.step()
  └─ scheduler.tick()      # A1 在这里启动/加负载/发伪造 DENM
  └─ sensing.tick()        # 产生 sensing.objects；A1 的 hook 在这里追加幽灵
  └─ v2x.tick()            # 读 extras 的额外负载 → CBR/PER/时延；发 CAM/CPM/DENM
  └─ uu / auth
  └─ control.tick()        # ADAS 读“被篡改后的目标列表” → control.command
  └─ task / edge
```

> 顺序很重要：**攻击调度在感知之前，控制在感知之后**。所以 A1 注册的 hook 和 `extra_load` 在同一个 tick 就生效；ADAS 消费的永远是“已经被改过”的目标列表。

## 2. 攻击如何被创建、何时开始

### 2.1 Web 与 CLI 的入口

Web 的请求体由 `AttackSpec.from_dict()` 转成攻击描述（[base.py](../isacsim/attacks/base.py:15)）：

```python
@dataclass
class AttackSpec:
    type: str
    count: int = 1
    target: str | None = None
    amplitude: float = 0.5
    duration: float = 12.0
    start: float | None = None      # 仿真时刻；None 表示立即
    params: dict[str, Any] = field(default_factory=dict)
```

`SessionManager.submit_attack()`（[session.py](../isacsim/web/session.py:92)）只做转发：

```python
spec = AttackSpec.from_dict(payload)
ids = self.sim.submit_attack(spec)
```

CLI 的 `-a A1 --attack-start 3 --amplitude 0.6` 走的是同一条路：`cmd_run()` 直接构造 `AttackSpec` 并调用 `sim.scheduler.submit()`（[cli.py](../isacsim/cli.py:66)）。

**`start` 是绝对仿真时刻，不是“延迟多少秒”。** Web 前端会把它换算成 `当前 sim_time + 用户填的延迟`（[app.js](../isacsim/web/static/app.js:406)）；CLI 的 `--attack-start 3` 就是“仿真到 3 s 时开始”。

### 2.2 `count > 1` 时如何错峰

`AttackScheduler.submit()`（[scheduler.py](../isacsim/attacks/scheduler.py:25)）：

```python
count = max(1, min(20, int(spec.count)))
for i in range(count):
    aid = f"{run_id}-ATK{self._counter:03d}"
    inst = cls(sub, self.scene, self.seed + i * 7919, aid)
    inst.offset = i * 2.0
    inst.start_at = -1.0
    self.instances.append(inst)
```

- 每个实例有自己的 `attack_id`（`ATK001`、`ATK002`…）；
- 每个实例的随机种子是 `seed + i * 7919`，所以多实例可能选到不同 RSU/车辆；
- 启动时间按 `i * 2.0 s` 错峰，避免同一 tick 一起爆发；
- `count` 被限制在 1–20。

### 2.3 开始与结束

真正的启动发生在 `AttackScheduler.tick()`（[scheduler.py](../isacsim/attacks/scheduler.py:48)）：

```python
if not inst.started:
    if inst.submitted_t is None:
        inst.submitted_t = ctx.t
        base = inst.spec.start if inst.spec.start is not None else ctx.t
        inst.start_at = base + inst.offset
    if ctx.t + 1e-9 >= inst.start_at:
        inst.start(ctx)
        ...
        self.truth.add(inst.truth())
        continue
else:
    if ctx.t >= inst.t1 - 1e-9:
        inst.stop(ctx)
        ...
    else:
        inst.tick(ctx)
```

`AttackInstance.start()`（[base.py](../isacsim/attacks/base.py:108)）只做两件事：

```python
self.started = True
self.t0 = ctx.t
self.t1 = self.t0 + self.spec.duration
```

`stop()`（[base.py](../isacsim/attacks/base.py:116)）会把注册过的 hook 全部摘掉：

```python
for stream, fn in self._hooks:
    ctx.hooks.off(stream, fn)
self._hooks.clear()
self.finished = True
```

因此 A1 的幽灵注入和额外负载都严格限制在 `[t0, t1)`；`t1` 之后不再加 `extra_load`，hook 也不再追加幽灵。

> 注意：`truth()` 是在 `start()` 之后立刻调用并落盘的，`t1` 是**计划值**。如果中途 `cancel`，真值里的 `t1` 不会改（见 §10）。

## 3. 选目标与生成幽灵目标

### 3.1 目标选择：稳定哈希，不是随机

A1 的 `start()`（[campaigns.py](../isacsim/attacks/campaigns.py:38)）：

```python
rsu = pick_rsu(self.scene, ctx, self.seed)
veh = pick_vehicle(ctx, self.seed, "a1")
if veh is None or rsu is None:
    self.finished = True
    return
```

`pick_rsu()` / `pick_vehicle()` 都在 [base.py](../isacsim/attacks/base.py:34)：

```python
def stable_pick(items, seed, salt):
    idx = zlib.crc32(f"{seed}:{salt}".encode()) % len(items)
    return items[idx]

def pick_vehicle(ctx, seed, salt=""):
    vids = sorted(ctx.vehicles)
    return ctx.vehicles.get(stable_pick(vids, seed, salt))

def pick_rsu(scene, ctx, seed):
    rsus = [s for s in scene.sensors if s.kind == "rsu"]
    return stable_pick(rsus, seed, "rsu")
```

- 同一 seed、同一车辆集合，选中的 RSU/车辆是确定的；
- 默认场景 seed=11 时，`pick_rsu()` 选到 **RSU-03**（x=340，yaw=180°）；seed=14 时选到 **RSU-01**；
- **没有检查受害车是否被该 RSU 覆盖，也没有检查它是否装备/有 ADAS**。这是后面“ADAS 分支不保证发生”的根因（§10.1）。
- `spec.target` 字段对 A1 **不生效**：代码始终用 `pick_vehicle()` 自己选，不读 `spec.target`。

### 3.2 幽灵目标的几何

`ghost_object()`（[base.py](../isacsim/attacks/base.py:62)）：

```python
def ahead(veh, dist, lateral=0.0):
    h = math.radians(veh.heading_deg)
    return (veh.x + math.cos(h) * dist - math.sin(h) * lateral,
            veh.y + math.sin(h) * dist + math.cos(h) * lateral)

def ghost_object(veh, oid, dist=30.0, cls="obstacle", lateral=0.0):
    x, y = ahead(veh, dist, lateral)
    return {
        "object_id": oid,
        "cls": cls,
        "x": round(x, 3),
        "y": round(y, 3),
        "z": 0.8,
        "l": 4.5 if cls == "car" else 0.6,
        "w": 1.8 if cls == "car" else 0.6,
        "h": 1.6 if cls == "car" else 1.8,
        "vx": 0.0,
        "vy": 0.0,
        "heading_deg": round(veh.heading_deg, 1),
        "confidence": 0.92,
        "tracked_age": 50,
        "occluded": False,
        "entity": f"ghost:{oid}",
    }
```

关键点：

- **幽灵是静止的世界坐标**，在 `t0` 时按受害车当时的位置算出来，之后不会跟着车走；
- `vx=vy=0`，所以 ADAS 算 TTC 时 `closing` 等于自车速度；
- `entity` 固定为 `ghost:<id>`，正常车辆是 `veh:<vid>`，静态物体是 `obj:<id>`，检测侧可区分；
- `confidence=0.92`、`tracked_age=50`，让它看起来像一个已经被稳定跟踪的目标；
- `l/w/h` 按 `car` / `obstacle` 给不同尺寸。

### 3.3 强度 `a` 决定幽灵数量与负载

`start()` 里：

```python
n = 1 + int(round(self.spec.amplitude * 4))
self.ghosts = [
    ghost_object(veh, 9000 + i,
                 dist=22.0 + 9.0 * i,
                 cls="car" if i % 2 == 0 else "obstacle",
                 lateral=0.4 * (i % 3) - 0.4)
    for i in range(n)
]
self.extra_load = _level(self.spec.amplitude, 150.0, 650.0)
```

`_level(a, lo, hi)` 的定义（[campaigns.py](../isacsim/attacks/campaigns.py:21)）：

```python
def _level(amp, lo, hi):
    return lo + (hi - lo) * max(0.0, min(1.0, amp))
```

所以：

| `a` | 幽灵数 `n` | 距离（m） | 类别（i=0,1,2…） | `extra_load`（msg/s） |
|---:|---:|---|---|---:|
| 0.5 | 3 | 22, 31, 40 | car, obstacle, car | 400 |
| 0.6 | 3 | 22, 31, 40 | car, obstacle, car | 450 |
| 0.75 | 4 | 22, 31, 40, 49 | car, obstacle, car, obstacle | 525 |
| 1.0 | 5 | 22, 31, 40, 49, 58 | car, obstacle, car, obstacle, car | 650 |

横向偏移是 `-0.4, 0, +0.4` 循环，全部落在 ADAS 的 `|lateral| <= 2.2 m` 判定内。

> Web 滑块的 `amplitude` 范围是 0.1–1.0；API 可以传更大的值。`n = 1 + round(4a)` 不夹取，`a=2` 会生成 9 个幽灵（距离最远 94 m，超出 ADAS 的 60 m 判定）；`extra_load` 则会被 `_level()` 夹到 650。本文的数值表只覆盖 `[0, 1]` 的常规范围。

包络判据只卡 `extra_load >= 250`（[campaigns.py](../isacsim/attacks/campaigns.py:94)），也就是 `a >= 0.2`；它**不要求** CBR 超阈值，也不要求真的发生制动。

### 3.4 一个实测例子（seed=14，a=0.6）

`t0=3.0 s` 时，受害车 `eastbound.2` 位于 `(19.477, -8.0)`，三个幽灵目标被放在：

| i | object_id | cls | x | y | 距车 |
|---:|---:|---|---:|---:|---:|
| 0 | 9000 | car | 41.477 | -8.4 | 22 m |
| 1 | 9001 | obstacle | 50.477 | -8.0 | 31 m |
| 2 | 9002 | car | 59.477 | -7.6 | 40 m |

同一帧 `sensing.objects` 原来是 3 个真实目标，注入后变成 6 个；幽灵的 `entity` 分别是 `ghost:9000/9001/9002`。

> 选择 seed=14 是因为它正好覆盖“目标 RSU 也是服务 RSU、受害车有 ADAS”的完整链路。seed=11/19 是反例，见 §10.1。

## 4. 注入点：为什么改 `sensing.objects` 就够了

### 4.1 所有记录都经过 `HookBus`

`SimContext.emit()`（[context.py](../isacsim/core/context.py:59)）：

```python
payload = self.hooks.apply(stream, payload, self)
if payload is None:
    return None
rec = Record(stream=stream, ts_ns=self.ts_ns(t), source=source,
             entity=entity, payload=payload)
self.sink.emit(rec)
if self.detector is not None:
    self.detector.on_record(rec)
return payload
```

`HookBus.apply()`（[context.py](../isacsim/core/context.py:31)）按注册顺序执行 hook：

```python
for fn in list(self._hooks.get(stream, ())):
    payload = fn(payload, ctx)
    if payload is None:
        return None
return payload
```

所以 hook 是“发射器输出侧”的唯一改写点：**记录还没有落盘、检测器还没有看到**。A1 在这里追加幽灵，落盘和检测器看到的都是被篡改后的版本；SUMO 世界状态不受影响。

### 4.2 A1 的 hook

```python
def hook(payload, _ctx):
    if payload.get("sensor_id") != self.rsu_id:
        return payload
    payload["objects"] = list(payload.get("objects", [])) + [
        dict(g) for g in self.ghosts
    ]
    return payload

self.hook(ctx, "sensing.objects", hook)
```

它只做三件事：

1. 只处理 `sensor_id == 目标 RSU` 的帧，其他 RSU/gNB 不受影响；
2. 在原有 `objects` 后面追加幽灵的浅拷贝；
3. 返回新 payload。

它**不改** `sensing.radar.echo`、`sensing.radar.track`。所以同一时刻：

- 雷达回波/点迹里只有真实车辆；
- 目标列表里多了 3 个幽灵；
- 这正是“跨层不一致”的来源，也是检测器可以利用的证据。

### 4.3 注入后的两条下游路径

`sensing._emit_frame()` 在 `ctx.emit("sensing.objects", ...)` 之后（[sensing.py](../isacsim/layers/sensing.py:213)）：

```python
final = ctx.emit("sensing.objects", sensor.id, f"rsu:{sensor.id}", payload, t=t)
if final is not None:
    self.last_objects[sensor.id] = final.get("objects", [])
    self.last_frame_t[sensor.id] = t
    ctx.extras[f"objects:{sensor.id}"] = final.get("objects", [])
```

`final` 是 hook 处理后的 payload，因此：

1. **ADAS 路径**：`ControlLayer` 读 `self.sensing.last_objects[sensor.id]`（[control.py](../isacsim/layers/control.py:56)），会看到幽灵；
2. **CPM 路径**：`V2XLayer` 读 `ctx.extras[f"objects:{sensor.id}"]`（[v2x.py](../isacsim/layers/v2x.py:118)），RSU 的 CPM 摘要里也会带幽灵；
3. **检测路径**：`sink` 落盘 + `ReferenceDetector.on_record()`，看到的是带幽灵的 `sensing.objects`。

> 注意：A1 的幽灵不会进入 `sensing.radar.echo/track`，也不会进入 SUMO 的车辆列表。它不是“凭空多了一辆车”，而是“路侧目标列表里多了一个目标”。

### 4.4 hook 的生命周期

- `self.hook(ctx, "sensing.objects", hook)` 在 `start()` 中注册，同时把 `(stream, fn)` 记到 `self._hooks`；
- `AttackInstance.stop()` 在 `t1` 时逐个 `ctx.hooks.off()` 并清空；
- 因此 `[t0, t1)` 内每帧都注入，`t1` 之后立即停止。

如果目标 RSU 在场景中不存在，`pick_rsu()` 会回退到 `scene.sensors` 的第一个；默认场景有 3 个 RSU，不会发生。

### 4.5 一个数据一致性瑕疵

`sensing.frame` 的 `object_count` 用的是**注入前**的局部变量 `objects`（[sensing.py](../isacsim/layers/sensing.py:223)）：

```python
ctx.emit("sensing.frame", ..., {
    "object_count": len(objects),   # 注入前的数量
    ...
})
```

而 `sensing.objects` 里是注入后的 `final`。实测 seed=14、t=3.0：

- `sensing.objects`：6 个目标（3 真 + 3 幽灵）；
- `sensing.frame.object_count`：3。

也就是说，`sensing.frame` 与 `sensing.objects` 在 A1 下会对不上。检测器目前不依赖 `sensing.frame.object_count`，但做数据校验时要注意（§10.5）。

## 5. 从幽灵目标到真实制动

### 5.1 ADAS 的准入门槛

`ControlLayer.tick()`（[control.py](../isacsim/layers/control.py:39)）对每辆车依次检查：

```python
if not is_equipped(v.vid, self.scene.vehicles.equipped_ratio):
    continue
if not has_adas(v.vid, self.scene.vehicles.adas_ratio):
    continue
if v.speed < 2.0:
    continue
if t - self.last_cmd_t.get(v.vid, -1e9) < 3.0:
    continue
```

- `is_equipped` / `has_adas` 都是 `crc32(vid)` 的稳定映射（[common.py](../isacsim/layers/common.py:5)），同一辆车在整个运行中属性不变；
- 默认 `equipped_ratio=0.9`、`adas_ratio=0.6`；
- 速度低于 2 m/s 不触发；同一辆车 3 s 内不重复发指令。

然后选“服务传感器”：

```python
sensor = serving_sensor(v, [s for s in self.scene.sensors if s.kind in ("rsu", "gnb")])
objects = self.sensing.last_objects.get(sensor.id, [])
hazard = self._find_hazard(v, objects)
```

`serving_sensor()` 选的是**覆盖该车且距离最近**的 RSU/gNB（[common.py](../isacsim/layers/common.py:17)）。如果目标 RSU 不是受害车的服务传感器，ADAS 读的是另一个传感器的目标列表，看不到幽灵。这是 §10.1 的第二个条件。

### 5.2 TTC 的计算

`_find_hazard()`（[control.py](../isacsim/layers/control.py:67)）：

```python
for o in objects:
    dx, dy = o["x"] - veh.x, o["y"] - veh.y
    longitudinal = dx * hx + dy * hy
    lateral = dx * px + dy * py
    if not (2.0 < longitudinal < 60.0):
        continue
    if abs(lateral) > 2.2:
        continue
    closing = veh.speed - (o.get("vx", 0.0) * hx + o.get("vy", 0.0) * hy)
    closing = max(closing, 0.2)
    ttc = longitudinal / closing
    if best is None or ttc < best[0]:
        best = (ttc, o)
```

对 seed=14、t=3.0 的第一个幽灵：

```text
longitudinal = 22.0 m
closing      = 14.857 - 0 = 14.857 m/s
TTC          = 22.0 / 14.857 = 1.481 s
```

`TTC_THRESHOLD = 2.5`（[control.py](../isacsim/layers/control.py:25)），所以 1.481 < 2.5，触发 `_command()`。

> 幽灵是静止的，`closing` 就等于自车速度；如果受害车速度很低（例如 < 8.8 m/s，22/2.5），TTC 会大于 2.5，不一定触发。攻击是否“制动”取决于车距和车速，不是只看 amplitude。

### 5.3 发出的制动指令

`_command()`（[control.py](../isacsim/layers/control.py:86)）：

```python
ctx.emit("control.command", source, f"veh:{veh.vid}", {
    "src": source,
    "dst": veh.vid,
    "cmd_type": "brake",
    "params": {"decel_mps2": dec, "ttc_s": round(ttc, 3)},
    "seq": self._seq[veh.vid],
    "sign_status": "valid",
    "reason": reason,
    "apply_after_ms": int(self.REACTION_S * 1000),
})
self.pending.append(PendingBrake(due_t=t + self.REACTION_S, ...))
ctx.extras.setdefault("brake_events", []).append({
    "vid": veh.vid, "x": veh.x, "y": veh.y,
    "cause": "emergency_brake" if reason != "injected" else "injected_brake",
})
ctx.extras["emergency_until"] = max(ctx.extras.get("emergency_until", 0.0), t + 3.0)
```

实测 seed=14 的第一条指令：

```json
{
  "stream": "control.command",
  "source": "adas:eastbound.2",
  "entity": "veh:eastbound.2",
  "payload": {
    "src": "adas:eastbound.2",
    "dst": "eastbound.2",
    "cmd_type": "brake",
    "params": {"decel_mps2": 3.0, "ttc_s": 1.481},
    "seq": 1,
    "sign_status": "valid",
    "reason": "ttc",
    "apply_after_ms": 120
  }
}
```

这条指令看起来是**完全正常的 ADAS 输出**：`src=adas:*`、`reason=ttc`、`ttc_s=1.481`。它不是攻击者伪造的 `control.command`；攻击者只改了目标列表。这一点对检测很重要：单看控制域，A1 的指令是“合理”的；要发现它，必须回到感知域找幽灵，或做跨层一致性检查。

对比 A2：

- A2 调用 `control.inject_brake()`，`source=attacker:ctl-<vid>`、`reason=injected`、`ttc_s=99`；
- A1 的 `ttc_s` 是真实算出来的（1.481），`source=adas:<vid>`。

### 5.4 从指令到 SUMO 减速

`_apply_pending()`（[control.py](../isacsim/layers/control.py:110)）在 `due_t = t + 0.12` 后执行：

```python
target = max(0.0, veh.speed - p.decel * p.duration)
ctx.sumo.slow_down(p.vid, target, p.duration)
```

`SumoBackend.slow_down()`（[sumo_backend.py](../isacsim/world/sumo_backend.py:193)）直接调用 TraCI：

```python
self.traci.vehicle.slowDown(vid, max(0.0, speed), max(0.0, duration))
```

默认 `decel=3.0`、`duration=1.2`（`_command` 默认值），目标速度是 `当前速度 - 3.0 * 1.2`。seed=14 实测：

| 仿真时刻 | `eastbound.2` 速度 |
|---:|---:|
| 3.0 s | 14.857 m/s |
| 3.3 s | 14.417 m/s |
| 4.0 s | 12.317 m/s |
| 4.2 s | 11.717 m/s |

速度从 14.86 降到 12.32（1 s 后），说明 `slow_down` 已在 SUMO 里落地，不是只写了一条记录。

### 5.5 谁会真的刹车

A1 的幽灵是注入到**目标 RSU 的目标列表**里的，所有以该 RSU 为服务传感器、且装备了 ADAS 的车辆都可能看到它。因此实际刹车的可能不止真值里的 `victim`。

seed=14、a=0.6、场景 15 s 的 `control.command`：

| 时刻 | 车辆 | TTC |
|---:|---|---:|
| 3.0 s | eastbound.2（真值 victim） | 1.481 |
| 7.0 s | eastbound.7 | 2.208 |
| 10.0 s | eastbound.7 | 0.663 |
| 10.0 s | eastbound.10 | 2.208 |
| 13.0 s | eastbound.10 | 0.644 |
| 13.0 s | eastbound.13 | 2.428 |

幽灵是静止的，后续车辆依次接近它，ADAS 依次刹车——这会在路上形成“幽灵拥堵”，也会让多辆车进入紧急制动状态。真值只记录一个 `victim`，但下游影响是扩散的。

> 这里有一个重要的代码层时序问题：A1 的 ADAS 指令虽然真的让车减速，但它**不会**触发 V2X 的 DENM/CAM 升频。原因见 §9.2。物理制动由 `ControlLayer.pending` 落地，和 `ctx.extras` 的丢失无关。

## 6. 从额外负载到信道拥塞

### 6.1 `ctx.extras` 是“每 tick 重建”的

`Simulation.step_once()` 每个 tick 都新建一个 `SimContext`（[engine.py](../isacsim/core/engine.py:117)），`extras` 是默认空 dict。因此 A1 不能只在 `start()` 里加一次负载，必须在**每个 tick** 重新加：

```python
def tick(self, ctx):
    ctx.extras["v2x_extra_load"] = ctx.extras.get("v2x_extra_load", 0.0) + self.extra_load
    ...
```

`scheduler.tick()` 在 `v2x.tick()` 之前执行，所以同一 tick 的 CBR 就能看到这笔负载。

### 6.2 信道公式

`V2XLayer._channel()`（[v2x.py](../isacsim/layers/v2x.py:36)）：

```python
n_eq = 已装备车辆数
rate = 10.0 * self.dcc_factor
cam_load = n_eq * rate
rsu_load = RSU 数 * 10.0
self.offered = cam_load + rsu_load + extra_load
self.cbr = min(0.98, 0.92 * self.offered / 1200.0 + jam)

if self.cbr > 0.65 and self.dcc_factor > 0.5:
    self.dcc_factor = max(0.5, self.dcc_factor - 0.1)
elif self.cbr < 0.55 and self.dcc_factor < 1.0:
    self.dcc_factor = min(1.0, self.dcc_factor + 0.05)

self.per = min(0.95, 0.01 + 0.85 * max(0.0, self.cbr - 0.55) / 0.45 + jam * 0.6)
self.delay_ms = 2.0 + 45.0 * self.cbr ** 3 + delay_bonus
```

A1 的 `jam=0`，所以：

```text
extra_load = 150 + 500a
offered    = 已装备车辆数 × 10 × dcc + 30 + extra_load
cbr        = min(0.98, 0.92 × offered / 1200)
per        = min(0.95, 0.01 + 0.85 × max(0, cbr − 0.55) / 0.45)
delay      = 2 + 45 × cbr³   (ms)
```

### 6.3 实测数值

seed=14、t=3.1（基线 `offered=120`，即 9 辆已装备车 + 3 个 RSU）：

| `a` | 幽灵数 | `extra_load` | `offered` | CBR | PER | 时延 |
|---:|---:|---:|---:|---:|---:|---:|
| 0.6 | 3 | 450 | 570 | **0.437** | 0.010 | 5.76 ms |
| 1.0 | 5 | 650 | 770 | **0.590** | 0.086 | 11.26 ms |

`a=1.0` 的场景时长 20 s（攻击 10 s）里，随着车辆增多，最高 CBR 到 **0.659**、PER 到 **0.2165**、时延 **14.9 ms**，DCC 因子降到 0.9。也就是说：

- `a=0.6`、t=3.1 时，CBR 从 0.092 跳到 0.437，还没到 PER 的拐点（0.55），所以 PER 仍是 0.01；随着车流增加，15 s 内最高 CBR 0.598、PER 0.1007；
- `a=1.0`、t=3.1 时，CBR 越过 0.55，PER 开始上升；场景 20 s 内最高 CBR 0.659、PER 0.2165；
- CBR 到 0.65 后 DCC 会降 CAM 频率，形成负反馈，所以不会无限增长；上限是 0.98。

> `extra_load` 是一个**抽象的信道负载**，不是“真的发了 450 条报文”。A1 的 `tick()` 只实际 emit 了 2 Hz 的伪造 DENM（10 s 约 20 条）；`extra_load` 代表这类攻击流量在信道模型里的等效 offered load。这是参数化信道模型，不是协议级逐包仿真。

### 6.4 伪造 DENM

`A1.tick()`（[campaigns.py](../isacsim/attacks/campaigns.py:66)）：

```python
if int(round(ctx.t * 2)) != int(round((ctx.t - ctx.step_s) * 2)):
    veh = ctx.vehicles.get(self.veh_id)
    x = veh.x if veh else 0.0
    y = veh.y if veh else 0.0
    ctx.emit("v2x.denm", "ATK-A1", "attacker:A1", {
        "sender_pseudo": "ATK-A1",
        "msg_type": "denm",
        "cause": "obstacle_warning",
        "posx": round(x + 30.0, 2),
        "posy": round(y, 2),
        "delay_ms": 3.0,
        "lost": False,
        "cbr": 0.0,
        "forged": True,
    })
```

- 约 2 Hz；由于 `round` 的取整方式，首条可能比 `t0` 晚 0.2–0.3 s；
- `posx = victim.x + 30 m`，不是幽灵的精确位置；
- `cbr=0.0`、`delay_ms=3.0` 是攻击者自己填的伪造值，**不是**信道实测值；真实值在 `link.metrics`；
- `forged=True` 是检测侧区分“攻击伪造”和“ADAS 真实触发”的标记；
- 这条记录走 `ctx.emit`，会被落盘和检测器看到，但不经过 A1 的 hook。

### 6.5 CPM 也会带幽灵

`V2XLayer` 的 CPM（[v2x.py](../isacsim/layers/v2x.py:113)）从 `ctx.extras[f"objects:{sensor.id}"]` 取目标摘要，而这个值是 hook 处理后的 `final`。所以目标 RSU 的 `v2x.cpm` 里，`object_count` 会包含幽灵。

seed=14、t=3.1 实测：RSU-01 的 `v2x.cpm.object_count=6`，摘要里能看到 `obstacle` 幽灵。它增加了 CPM 的内容，但**不是** A1 拥塞的主要来源；主要来源仍是 `extra_load`。

> 在本模拟器里，ADAS 消费的是 `sensing.last_objects`，不是 `v2x.cpm`。所以 CPM 带幽灵是“对外广播”的效果，不是 ADAS 制动的直接原因。

### 6.6 DCC、PER 与告警阈值

- `DCC`：`cbr>0.65` 时每步降 `dcc_factor` 0.1（下限 0.5）；`cbr<0.55` 时每步升 0.05（上限 1.0）。它会让 CAM 频率下降，从而部分抵消负载。
- `PER`：`cbr<=0.55` 时保持 0.01；越过 0.55 后线性上升；`link_degraded` 规则要求 `per > 0.5`。
- `cbr_spike` 规则要求 `cbr > 0.7` 且 3 s 内上升 >0.2；`a=0.6`（场景 15 s）的最高 CBR 是 0.598，`a=1.0`（场景 20 s）的最高 CBR 是 0.659，都未达到 0.7。
- 因此在这些短场景里，检测器通常只能报 `ghost_object`；`cbr_spike`/`link_degraded` 要等车流更密、CBR 更高时才可能出现。

## 7. 真值事件：写了什么、没写什么

### 7.1 写入时机

`AttackScheduler.tick()` 在 `inst.start(ctx)` 之后立刻：

```python
self.truth.add(inst.truth())
```

`TruthStore.add()`（[model.py](../isacsim/truth/model.py:78)）把事件追加到 `truth/events.jsonl` 并 flush。因此真值是在 `t0` **预先声明**的，不是等攻击结束再回填。

### 7.2 A1 的真值样例

seed=14、a=0.6、攻击时长 10 s（场景 15 s）的实际输出（节选）：

```json
{
  "event_id": "EVT-arterial-14-...-ATK001",

  "official_type": "感知数据篡改诱导通信拥塞",
  "label": 1,
  "t0": 3.0,

  "nodes": ["rsu:RSU-01", "veh:eastbound.2", "attacker:A1"],
  "domains": ["perception", "v2x", "control"],
  "params": {
    "ghost_count": 3,
    "extra_load": 450.0,
    "rsu": "RSU-01",
    "victim": "eastbound.2"
  },
  "amplitude": 0.6,
  "envelope": {
    "in_envelope": true,
    "criterion": "extra_load >= 250 msg/s"
  },
  "stages": [
    {"name": "伪造路侧目标", "t0": 3.0, "t1": 5.0},
    {"name": "通信负载上升", "t0": 5.0, "t1": 13.0}

```

字段来源：

- `nodes` / `params` / `envelope` / `expected_evidence` 由 `CampaignA1.truth()` 写（[campaigns.py](../isacsim/attacks/campaigns.py:87)）；
- `causal_chain` 来自 `OFFICIAL_CHAIN["A1"]`（[model.py](../isacsim/truth/model.py:22)）；
- `domains` 固定为 `["perception", "v2x", "control"]`；
- `stages` 由 `truth()` 按 `t0/t1` 计算，是**计划**，不是运行时状态。

### 7.3 三个“不要误读”

1. **`stages` 不是运行时事件**。A1 的 `extra_load` 从 `t0` 就开始加，`stages` 却把“通信负载上升”写在 `t0+2`；`t0+2` 只是一个叙述分界，不是代码里的开关。
2. **`domains` 是“声明”，不是“保证”**。即使受害车没装备/没被目标 RSU 覆盖、根本没有 `control.command`，`domains` 里仍然有 `control`。
3. **`expected_evidence` 是“期望证据”，不是“必然出现的文件”**。例如 seed=11 的受害车 `westbound.0` 没有装备，不会产生 `control.command`；但真值里仍然列了它。

`envelope` 只检查 `extra_load >= 250`，不检查 CBR/PER/制动；所以 `in_envelope=true` 只代表“负载达到了 A1 的包络门槛”，不代表“拥塞/制动一定发生”。

## 8. 检测侧看到了什么

参考检测器只读观测记录，不读真值（[reference.py](../isacsim/detect/reference.py:64)）。A1 相关的规则主要有三条。

### 8.1 `ghost_object`

`_on_objects()`（[reference.py](../isacsim/detect/reference.py:83)）：

- 只看 `cls in ("stop_sign", "obstacle")`；
- 如果目标靠近 `scene.static_objects` 中已有地图物体（3 m 内），跳过；
- 如果另一个传感器在 2.5 m 内也看到同一目标，认为是“多 RSU 互证”，跳过；
- 连续 2 帧都未确认，才报 `ghost_object`；
- 同一 `rule:entity` 1 s 内去重。

A1 的幽灵只注入一个 RSU，所以不会被多 RSU 互证；`obstacle` 类幽灵会被这条规则命中。实测 seed=14：

```json
{"t": 3.1, "rule": "ghost_object", "entity": "rsu:RSU-01",
 "detail": {"x": 50.477, "y": -8.0, "cls": "obstacle"},
 "latency_ms": 0.106}
```

注意：`car` 类幽灵（i=0、2）**不会**被 `ghost_object` 命中；只有 `obstacle`（i=1）会。A1 的 `n` 在 `a` 很小（例如 `a<=0.12`）时可能只有 1 个 `car`，此时这条规则完全不会触发，只能靠 CBR/时延等后果证据。

### 8.2 `cbr_spike` / `link_degraded`

`_on_link()`（[reference.py](../isacsim/detect/reference.py:159)）：

```python
if cbr > 0.7 and rise > 0.2:
    alert("cbr_spike", ...)
if per > 0.5:
    alert("link_degraded", ...)
```

在 `a=0.6`（场景 15 s）的实测里，最高 CBR 是 0.598、最高 PER 是 0.1007；`a=1.0`（场景 20 s）的最高 CBR 是 0.659、最高 PER 是 0.2165。两组都未触发 `cbr_spike`（需 CBR>0.7）和 `link_degraded`（需 PER>0.5）。

### 8.3 `brake_without_hazard`

`_on_control()`（[reference.py](../isacsim/detect/reference.py:171)）在 `ttc_s >= 10` 时告警。A1 的 `ttc_s` 是 1.481，不会触发；这条规则主要抓 A2 的 `inject_brake(ttc=99)`。

### 8.4 跨层证据

A1 的可检测性主要来自“同一时刻、不同来源对不上”：

| 证据 | A1 下的表现 |
|---|---|
| `sensing.objects` vs `sensing.radar.track` | 目标列表多出幽灵，雷达没有对应回波/点迹 |
| `sensing.objects` vs 地图先验 | 幽灵不在 `scene.static_objects` 里 |
| 单 RSU vs 多 RSU | 只有目标 RSU 看到幽灵，其他 RSU 没有 |
| `control.command` vs 目标列表 | 制动指令的 TTC 来自幽灵，但指令本身“看起来正常” |
| `link.metrics` vs 申报负载 | CBR 上升，但伪造 DENM 的 `cbr=0.0` 不可信 |

这也是为什么 A1 不能只靠控制域规则发现：它产生的是一条合法的 ADAS 指令。

## 9. 一次 A1 的时序

以 seed=14、a=0.6、t0=3.0 为例。

### 9.1 代码顺序

| 相对 `t0` | 发生什么 | 代码/数据 |
|---:|---|---|
| 0 | 调度器启动 A1，写真值，注册 hook | `scheduler.tick` → `CampaignA1.start` |
| 0 | `extra_load=450` 写入 `ctx.extras` | `CampaignA1.tick` |
| 0 | `sensing.objects` 追加 3 个幽灵 | `sensing._emit_frame` → hook |
| 0 | `last_objects` / `extras["objects:RSU-01"]` 变成 6 个目标 | `sensing.py:215-217` |
| 0 | ADAS 看到幽灵，TTC=1.481，发 `control.command` | `control.tick` → `_command` |
| 0 | `pending` 记录 0.12 s 后执行；`brake_events`/`emergency_until` 写入 `ctx.extras` | `control.py:102-108` |
| +0.05 | `v2x` 读 `extra_load`，CBR 上升；伪造 DENM 继续 | `v2x.tick` |
| +0.1 | 第一条带新 CBR 的 `link.metrics` | `v2x.py:158` |
| +0.1 | 第一条 `ghost_object` 告警 | `ReferenceDetector` |
| +0.15 | `slow_down` 落地，车速开始下降 | `_apply_pending` → `sumo.slow_down` |
| +0.5 | 下一条伪造 DENM（约 2 Hz） | `CampaignA1.tick` |
| `t1` | 摘 hook，停止加负载/发 DENM | `AttackInstance.stop` |

### 9.2 一个容易误解的点：ADAS 制动不会触发 V2X 的 DENM/CAM 升频

`control._command()` 把 `brake_events` 和 `emergency_until` 写进 `ctx.extras`（[control.py](../isacsim/layers/control.py:104)），但：

- `v2x.tick()` 在 `control.tick()` **之前**执行（[engine.py](../isacsim/core/engine.py:126)）；
- `ctx.extras` 每个 tick 都是新的空 dict（`step_once` 新建 `SimContext`）；
- 所以 control 在本 tick 写进去的 `brake_events` / `emergency_until`，到下一个 tick 已经不存在，`v2x.tick()` 永远读不到。

实际结果：

- A1 的 ADAS 指令**能**让车减速（`pending` 是 `ControlLayer` 的持久状态）；
- 但 A1 **不会**产生 ADAS 触发的 `v2x.denm`；
- A1 **不会**把 CAM 升到 20 Hz（`emergency_until` 丢失）。

实测 seed=14 的 15 s 场景：

- `v2x.denm` 共 20 条，全部是 `source=ATK-A1` 的伪造 DENM；
- 受害车 `eastbound.2` 的 `v2x.cam.rate_hz` 全程 10.0，没有 20 Hz；
- 但车速确实从 14.86 降到 12.32（`slow_down` 生效）。

这与 [07-实现原理与数据生成](07-实现原理与数据生成.md:517) 里“t0+0.2 该车 DENM；CAM 升频到 20 Hz”的时序描述不一致。按当前代码，A1 的 V2X 影响主要是 `extra_load` + 伪造 DENM，**不是** ADAS 制动带来的 DENM/CAM 升频。

> A2/A3 不受这个顺序问题影响：它们在 `scheduler.tick()` 里调用 `inject_brake()`，发生在 `v2x.tick()` 之前，所以 `brake_events` 能在同一 tick 被 V2X 消费。A1 的制动发生在 `control.tick()`，在 V2X 之后，才会丢。

## 10. 代码走读发现的差异与边界

以下都是“按当前 master 代码”的实际行为，不是设计文档里的理想链路。

### 10.1 受害车不保证被目标 RSU 覆盖，也不保证有 ADAS

`CampaignA1.start()` 只做 `pick_rsu()` + `pick_vehicle()`，两个选择互相独立，没有检查：

- 受害车是否在目标 RSU 的覆盖范围内；
- 受害车是否 `is_equipped`；
- 受害车是否 `has_adas`；
- 受害车的服务传感器是否就是目标 RSU。

实测三个 seed：

| seed | 目标 RSU | victim | 装备/ADAS | 服务传感器 | `control.command` |
|---:|---|---|---|---|---|
| 11 | RSU-03 | westbound.0 | 未装备 / 有 ADAS | RSU-03 | **无** |
| 14 | RSU-01 | eastbound.2 | 已装备 / 有 ADAS | RSU-01 | **有**（TTC=1.481） |
| 19 | RSU-02 | eastbound.1 | 已装备 / 有 ADAS | RSU-01 | **无**（覆盖不匹配） |

- seed=11：受害车未装备，`ControlLayer.tick()` 第一道 `is_equipped` 就跳过；
- seed=19：目标 RSU 是 RSU-02，但受害车在 x=37.9，最近的是 RSU-01，ADAS 读 RSU-01 的目标列表，看不到 RSU-02 里的幽灵。

**后果**：A1 的“感知 → ADAS → 制动”不是必然发生；但“幽灵注入 + `extra_load` + 伪造 DENM”仍然发生，所以 A1 作为“通信负载上升”仍然成立，只是没有物理制动这一环；是否真的形成严重拥塞，还取决于车流密度和 `a`。真值的 `domains` 仍然写 `control`，`expected_evidence` 仍然列 `control.command`，会高估实际链路。

**修复方向（未实施）**：先选受害车，再取它的 `serving_sensor` 作为目标 RSU；或在 `pick_vehicle` 后过滤 `is_equipped` / `has_adas` / 覆盖。

### 10.2 `ctx.extras` 的跨 tick 丢失

见 §9.2。影响：

- A1 的 ADAS 制动不会产生 DENM，也不会让 CAM 升到 20 Hz；
- 真值/文档里“denm:flood”仍然有伪造 DENM，但不是 ADAS 触发的那条；
- 如果演示时预期“刹车 → DENM → 更拥塞”的连锁，实际只能看到“刹车”和“额外负载”，看不到 ADAS DENM。

**修复方向（未实施）**：把 `brake_events` / `emergency_until` 放到 `ControlLayer` 的持久状态，或调整层序让 `control` 在 `v2x` 之前（但会改变“控制消费感知”的因果顺序，需要谨慎）。

### 10.3 真值的 `stages` / `domains` / `expected_evidence` 是声明，不是运行时事实

- `stages` 的“通信负载上升”从 `t0+2` 开始，但 `extra_load` 从 `t0` 就开始；
- `domains` 固定包含 `control`，即使没有 `control.command`；
- `expected_evidence` 包含 `control.command`，但 seed=11/19 不会产生。

**影响**：如果拿真值字段做演示脚本/评估解释，会“说的比跑的多”。建议把 `stages` 标成 `planned`，或从实际事件生成。

### 10.4 `cancel` 只置 `finished`，不摘 hook

`AttackScheduler.cancel()`（[scheduler.py](../isacsim/attacks/scheduler.py:77)）：

```python
for inst in self.instances:
    if inst.id == attack_id and not inst.finished:
        inst.finished = True
        return True
```

它没有调用 `inst.stop(ctx)`，所以：

- A1 的 `sensing.objects` hook 仍然挂在 `HookBus` 上；
- 即使 `tick()` 因 `finished` 不再加负载/发 DENM，幽灵仍会继续被追加到目标列表，直到 run 结束；
- `stats.campaign_finished()` 也不会调用。

**影响**：Web 上点“中止”后，A1 的幽灵不会立刻消失；演示时不要用“中止”来结束 A1 的注入，等 `t1` 自然结束更干净。

### 10.5 其他小差异

- `sensing.frame.object_count` 用注入前的 `objects`，与 `sensing.objects.objects` 不一致（§4.5）。
- 幽灵 `object_id` 固定从 9000 开始；多个 A1 实例同时注入到同一个 RSU 时，ID 可能重复（每个实例的种子不同，RSU 可能不同，但不是绝对）。
- `ghost_object` 只覆盖 `stop_sign`/`obstacle`；A1 的 `car` 类幽灵不会被这条规则命中。
- A1 的 `spec.target` 不生效，受害车始终由 `pick_vehicle()` 选。
- `v2x.denm` 里伪造记录的 `cbr=0.0`、`delay_ms=3.0` 是攻击者填的值，不是信道实测；不要拿它当链路质量证据。

## 13. 小结

A1 的实现可以概括为：

```text
目标列表追加幽灵（sensing.objects）
        │
        ├─ ADAS 看到 → TTC < 2.5 → control.command → SUMO slow_down
        │       （仅在装备 + ADAS + 目标 RSU 服务时成立）
        │
        └─ RSU CPM 摘要带幽灵

每个 tick 加 extra_load → CBR/PER/时延上升
每 0.5 s 伪造 DENM → 检测侧可见的 forged 记录
```

它不是“脚本直接刹车”，也不是“逐包洪泛”；它是**在感知输出侧注入假目标 + 在信道模型里加等效负载**，让系统自己做出制动和拥塞反应。理解这一点，才能解释为什么 A1 的 `control.command` 看起来是合法的、为什么检测要靠跨层一致性，以及为什么当前代码下“ADAS 制动 → DENM 升频”这条链实际上没有接通。

> 如何把这条链做成可观察、可暂停的追踪页面，见 [运行追踪与单步设计](trace/README.md)。
