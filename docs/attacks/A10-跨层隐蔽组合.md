# A10 跨层隐蔽组合：代码走读与实现解析

> 代码基线：`feature/trace-watch`（v0.3.0 + A1–A10 TraceProfile），2026-11-03。
> 共享机制见 [A1 §2–§4](A1-感知篡改诱导通信拥塞.md)；本文只写 A10 的差异。
> 目标：解释“雷达渐偏 + 轻度信令 + 审计抑制 + 小制动”的组合路径，并说明哪些是隐蔽性设计、哪些只是声明。

## 1. 一句话概括

A10 做四件事：

1. 对 victim 的 `sensing.radar.echo.range_m` 做线性渐偏（`bias_max = 1 + 2a`）；
2. 每 0.2 s 发 5 条 `core.nas` bot 注册（约 25 条/s），并把 AMF 负载提示设为 0.70；
3. 写一条 `app.audit` 后再 `suppress(2)`，制造审计序列缺口；
4. 在时长 60% 处注入两次 `inject_brake(1.2, 0.8)`，并再制造两次审计缺口。

它比 A5 轻、比 A3 多一层信令/审计噪声；目的是让单一域看起来都不够异常。

## 2. 端到端调用链

```text
POST /api/attacks {type:"A10", amplitude, duration, start}
  → CampaignA10.start(ctx)                campaigns.py:750
      ├─ 需要 core + platform
      ├─ pick_vehicle(seed,"a10")
      ├─ 注册 sensing.radar.echo hook
      ├─ core.amf.load_hint=0.70
      ├─ core.amf.queue_depth=capacity×0.70
      └─ audit.append(probe) + audit.suppress(2)
  → 每 0.2 s CampaignA10.tick(ctx)        campaigns.py:778
      ├─ 5 条 core.nas bot 注册
      └─ t >= t0 + duration×0.6 且 _audit_n<2：
          audit.append(probe) + audit.suppress(1)
          control.inject_brake(1.2, 0.8)
  → stop(ctx)                             campaigns.py:804
      └─ amf.load_hint=0, queue_depth=0
```

层序：

```text
scheduler → sensing → v2x → uu → core → auth → platform → control
```

- 雷达 hook 在 sensing 生效；
- bot `core.nas` 在 scheduler emit，core 层同一 tick 能看到 AMF 负载；
- 审计事件在 platform tick 之前 emit，平台 audit 状态直接改；
- 小制动在 scheduler 调用，同一 tick 进控制面。

## 3. 参数

| 量 | 公式 | `a=0.8` 实测 |
|---|---|---:|
| 最大偏置 | `1.0 + 2.0a` m | 2.6 m |
| 信令 | 每 0.2 s 5 条 | 25 条/s |
| AMF 负载提示 | 固定 0.70 | 0.70 |
| 审计抑制 | 开始时 2 条；60% 处每次 1 条，最多 2 次 | 4 条 |
| 制动 | 1.2 m/s²，0.8 s | 1.2 |
| 包络 | `bias >= 1.0m 且 signaling >= 2×` | true |

`signaling_rate` 在真值里固定写 25.0，不随 amplitude 变；`bias_max` 随 amplitude 变。

## 4. 注入点

### 4.1 雷达渐偏

```python
def hook(payload, _ctx):
    if payload.get("entity") != entity:
        return payload
    frac = max(0.0, min(1.0, (_ctx.t - self.t0) / max(self.spec.duration, 1e-6)))
    payload["range_m"] = round(float(payload["range_m"]) + self.bias_max * frac, 3)
    return payload

self.hook(ctx, "sensing.radar.echo", hook)
```

和 A3 相同，只是 `bias_max` 不同；点迹仍由被改回波派生。

### 4.2 轻度信令

```python
for i in range(5):
    ctx.emit("core.nas", f"ue:bot-a10-{i}", "amf:AMF-01", {
        "msg_type": "registration_request",
        "ue_id": f"bot-a10-{i}",
        "gnb_id": "GNB-01",
        "result": "reject",
        "cause": "congestion",
        "bot": True,
        "latency_ms": 8.0,
    })
```

每 0.2 s 一次，5 条；1 s 内 25 条，超过 `nas_registration_flood` 的 10 条门槛。它不是 A5 的 50 条/0.1 s，但仍然会被检测到。

### 4.3 审计抑制

```python
platform.audit.append(ctx, actor="attacker:A10", action="probe",
                      resource="audit", result="accept")
platform.audit.suppress(2)
```

`AuditLog.suppress()`（[audit.py](../../isacsim/layers/platform/audit.py:47)）只推进 `seq`，不写记录：

```python
def suppress(self, n=1):
    self.seq += n
    self.suppressed += n
```

检测器看到下一条 `app.audit` 的 `audit_seq` 跳号，就报 `audit_gap`。

在 60% 处：

```python
if self._audit_n < 2 and ctx.t >= self.t0 + duration*0.6:
    self._audit_n += 1
    audit.append(probe)
    audit.suppress(1)
    control.inject_brake(1.2, 0.8)
```

因为每 tick 都满足条件，`_audit_n` 会从 0→1→2，连续两 tick 各注入一次制动；实测 `control.command` 2 条。

### 4.4 AMF 负载

```python
core.amf.load_hint = 0.70
core.amf.queue_depth = int(core.amf.queue_capacity * 0.70)
```

这是直接改 AMF 的展示状态，不经过 `set_overload`；`overloaded` 仍为 False。`core:amf` 健康度会因 load_hint 变橙/红，但不会 emit `amf_overload` 事件。

## 7. 检测侧看到了什么

| 规则 | 触发 | 实测 |
|---|---|---|
| `nas_registration_flood` | 1 s 内 ≥10 条 bot 注册 | 3 条 |
| `audit_gap` | `audit_seq` 跳号 | 1 条 |
| `brake_without_hazard` | ttc>=10 | 1 条 |
| `radar_range_bias` | 5 帧 + 连续 3 次残差>1.5 | 短场景可能不出现 |

seed=14、a=0.8、3 s 攻击实测：

```text
nas_registration_flood ×3, audit_gap ×1,
brake_without_hazard ×1
```

雷达规则没有在 3 s 内触发；不要把“有渐偏”写成“必然告警”。

## 8. 外部检测视角：数据支撑、`/trace` 位置与 `out/` 落点

> 本节假设判定在仿真之外完成：只看导出的观测流与日志，不读 `truth/`、不读 `ctx.extras`。可观测面清单与路径/落盘规则见 [A1 §9.1、§9.4](A1-感知篡改诱导通信拥塞.md)。

### 8.1 判定 A10 需要的数据支撑

A10 的每个动作都刻意压低强度：雷达只偏 1–3 m、信令只有 25/s（A5 是约 500/s）、审计只吞 1–2 条、制动只有 1.2 m/s²。单看任何一路都只是“弱异常”，判定必须做**跨层弱证据的联合**。

| 观测面 | 需要捕获的字段 | 在判定中的作用 | 可依赖度 |
|---|---|---|---|
| `sensing.radar.echo` / `track` | `entity`、`frame_seq`、`range_m`、`pos_x/pos_y` | 残差缓增（同 A3，但更小），单帧低于常规门限 | 物理证据 |
| `core.nas` | `msg_type`、`ue_id`、`result`、`cause`、`bot`、`latency_ms` | 每 0.2 s 5 条、共 25/s 的注册拒绝，刚过 10 条/s 门槛 | `bot` 是标记；速率是协议证据 |
| `app.audit` | `audit_seq`、`prev_hash`、`hash`、`actor`、`action` | `audit_seq` 跳号（实测 1,2,5,7：缺 3/4/6）；哈希链本身仍闭合（`prev_hash` 指向上一条已写记录） | 物理证据（可验证） |
| `core:amf` 状态 | `load_hint`、`queue_depth`、`health` | `load_hint=0.7`、队列 70%，但**没有** `amf_overload` 事件 | 状态证据（`out/` 无快照） |
| `control.command` | `params.decel_mps2`、`params.ttc_s` | 两条 `ttc=99`、`decel=1.2` 的小制动 | 物理/协议证据 |
| `sensing.objects` / `v2x.cam` / `sensing.gnss` | 位置、速度 | 正常 → 排除 A1/A4 | 反证 |
| `link.metrics` | `cbr`、`jam` | 不变 → 排除 A1/A2 | 反证 |

判定口径：

```text
T1 雷达残差缓增（同 A3 的 K1），幅度 1–3 m，单帧低于门限。
T2 1 s 内注册请求 >10 条，但远低于 A5 的量级（25/s 对 500/s）→ “轻度信令”。
T3 app.audit 的 audit_seq 出现跳号（每次缺 1–2 条），而 prev_hash/hash 链仍能闭合
   → 不是写入失败，而是“被跳过的审计”。
T4 control.command 的 ttc_s=99、decel<=1.5，共两条。
=> T1∧T2∧T3 判“跨层隐蔽组合”；T4 是动作证据。单看任一条都只能判“弱异常”。
```

边界：

- AMF 的 `load_hint/queue_depth` 是直接改的状态，不走 `set_overload`，所以**没有** `amf_overload` 事件；不要拿“没有过载事件”否定；
- 审计抑制只推进 `seq`，被吞的记录不会出现在任何流里，只能靠序号缺口与平台侧 `suppressed` 计数发现；
- `signaling_rate=25` 是真值里的固定值，实际是 5 条/0.2 s；
- `nodes` 里的 `rsu:RSU-01` 是硬编码字符串，不是动态选择；
- 短场景（尤其 3 s 级）可能凑不满“5 帧 + 连续 3 次”，静默不等于没有偏置；4 s 以上的攻击在实测里就能触发 `radar_range_bias`。

### 8.2 对应前端 `/trace` 的位置

| 数据 | `/trace` 位置 | 看什么 |
|---|---|---|
| 雷达渐偏 | 右栏 **TRACE** 的 `radar.echo` / `radar.track` 事件 | `range_m` 缓增；只有采样，没有残差 |
| 轻度信令 | **核心网** → AMF 节点；右栏 `core.nas` 事件 | AMF 橙/红（`load 70%`），指标 `queue_depth` 高；事件 `registration_request reject (congestion) ×5` |
| 审计缺口 | **平台** → `平台 · V2X` 概览；右栏 `app.audit` | `audit_seq` 跳号、`audit_suppressed` 上升；下一条 `app.audit` 的 `actor=attacker:A10` |
| 小幅制动 | **车辆** → `<victim> · state`；右栏 `control.command` | `decel=1.2`、`ttc=99`（两条） |
| 告警 | **总览** → `Detector · alerts`；**底栏时间轴** | `nas_registration_flood`、`audit_gap`、`brake_without_hazard`；雷达规则取决于窗口 |
| 阶段 | 顶栏 **下一步** 后的检查点横幅 | S1 雷达回波渐偏 → S2 轻度注册信令 → S3 审计抑制 → S4 小幅制动 → S5 告警 |

不在 `/trace` 上的：被抑制的审计记录本身（只有序号缺口）、AMF `load_hint` 明细（节点卡只显示 4 个指标，reasons 里才有）、雷达残差序列。

## 9. 时序

| 相对 `t0` | 事件 |
|---:|---|
| 0 | 雷达 hook；AMF 负载 0.70；审计 append + suppress(2) |
| +0.05 | 第一批 5 条 bot 注册 |
| +0.2 | 下一批 bot 注册 |
| +1.0 | `nas_registration_flood` |
| +1.8 | 第一次审计缺口 + 小制动 |
| +1.85 | 第二次审计缺口 + 小制动（`_audit_n=2`） |
| `t1` | 清除 AMF load_hint/queue_depth |

## 10. 边界与差异

1. **`signaling_rate=25` 固定**：不随 amplitude 变；amplitude 只改雷达偏置。
2. **AMF 负载是展示状态**：没有 `overloaded=True`，也没有 `amf_overload` 事件。
3. **审计抑制不删除已有记录**：只推进 `audit_seq`，制造缺口。
4. **两条小制动**：60% 条件在每个 tick 都成立，`_audit_n` 允许两次。
5. **`nodes` 的 RSU-01 硬编码**：victim 可能不在 RSU-01 覆盖内。
6. **`stop` 只清 AMF 负载**：不恢复审计序列，也不撤销已注入制动。
7. **雷达规则可能不触发**：短场景/低 amplitude 下残差达不到 1.5 m。

## 13. 小结

```text
radar.echo 渐偏（bias_max=1+2a）
        +
每 0.2 s 5 条 bot 注册（25/s）
        +
audit append + suppress（seq 缺口）
        +
60% 处两次 inject_brake(1.2, 0.8)
        │
        ├─ nas_registration_flood
        ├─ audit_gap
        └─ brake_without_hazard
```

A10 的“隐蔽”不是单点不可见，而是把雷达、信令、审计、控制四个域的异常都控制在“单独看都不够确定”的强度；检测需要跨域关联。
