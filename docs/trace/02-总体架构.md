# 02 总体架构

> **当前状态（2026-10-30）**：TraceService、A1/A5 profile、Core/Platform provider、事件映射、`pause_at` 层边界暂停已实现；增量 SSE、trace.jsonl、回放、origin、focus 未实现。
> 实现差异见 [12 当前实现状态](12-当前实现状态.md)；本文保留目标架构，不把规划组件写成现状。

## 1. 设计约束

- 仿真主循环在后台线程里跑（`web/session.py` → `Simulation.run`），每步 50 ms；
- 观测记录统一经过 `SimContext.emit()`，落盘/检测都在这里发生（[context.py](../../isacsim/core/context.py)）；
- 攻击注入集中在 `HookBus.apply()`（[context.py](../../isacsim/core/context.py)）；
- 现有 Web 只有一个 SSE `/api/stream`，150 ms 推一次完整快照（[api.py](../../isacsim/web/api.py)）；
- 不引入新服务、新数据库、前端构建步骤。

因此新增部分应是一个**进程内的 TraceService**，与 `Simulation` 同生命周期，通过 FastAPI 暴露 REST/SSE。

不改攻击/检测/真值的核心逻辑；对 `Simulation`/`HookBus` 只加可选 observer。

## 3. 职责边界

### 3.1 Simulation

只增加**最小挂钩**：

- 每个 tick 的 `scheduler.tick()` 之后通知 `TraceService.after_scheduler(ctx)`（A5 S0）；
- 每个 tick 结束后通知 `TraceService.after_tick(ctx)`；
- `core.tick()` / `platform.tick()` 后通知 `TraceService.after_layer(name, ctx)`（A5 S1–S3）；
- `ctx.emit()` 后通知 `TraceService.on_record(rec)`；
- `Simulation.pause_at(reason)` 用 Condition 在安全边界停住仿真线程；
- 不把 trace 逻辑写进攻击/检测代码。

> 设计上不建议让 `TraceService` 反向控制 `Simulation`；控制通过 `StepController` 发信号，仿真线程在安全边界（scheduler 后 / tick 末尾）响应。

### 3.2 TraceService

- 拥有 `WatchRegistry`、`TraceStore`、`StepController`；
- 不读真值（除非显式 `demo_truth=true`）；
- 不改变 payload；
- 采集失败时 **fail-open**：trace 报错/停用，仿真继续。

### 3.3 Probe

> 下表是目标设计；当前由 `TraceService` 的 `on_record`/`after_tick`/provider 直接完成，独立 `Probe` 类、HookProbe、TruthProbe 未实现。

每个 Probe 只负责“从某个源取数 → 写 Store”，不负责渲染/讲解：

| Probe | 源 | 产出 |
|---|---|---|
| `RecordProbe` | `ctx.emit` 后的 `Record` | 事件、watch 字段更新、原始记录引用 |
| `HookProbe` | `HookBus.apply` 的 before/after | 攻击改了什么、丢弃了什么 |
| `StateProbe` | tick 末尾的 `vehicles`/`V2XLayer`/`ControlLayer`/`Detector` | 车辆、PC5、DET 的 watch 帧 |
| `AttackProbe` | `AttackScheduler`/`AttackInstance` | 攻击生命周期、阶段、目标 RSU/victim/参数 |
| `TruthProbe` | `TruthStore` | 真值事件（可选命名空间） |

### 3.4 TraceStore

- 写：仿真线程（单写者）；
- 读：FastAPI 线程 / SSE 协程（多读者）；
- 用锁或读写锁保护；
- 有界：每个 target 保留最近 N 帧/事件；StepFrame 单独保留；
- 可选落盘：`out/<run>/trace/events.jsonl`、`watch.jsonl`、`steps.jsonl`。

### 3.5 BreakpointController / StepController

- 在安全边界判定检查点：`after_scheduler` / `after_layer:core|platform` / `after_tick`；
- 命中后 A1 用 tick 末尾 `pause()`，A5 的 S0/S1/S2/S3 用 `pause_at()` 阻塞；
- 与仿真线程用 `Condition` 同步，避免 `pause()` 状态先变、线程未停稳的竞态；
- 同一层边界可连续暂停多个阶段（A5 S1→S2）；
- 详细设计见 [05 单步断点与时间模型](05-单步断点与时间模型.md)。

## 4. 三种模式

### 4.1 实时（live）

- 仿真连续跑；
- trace 每 tick/每事件写 ring buffer；
- SSE 以 10 Hz 推送“有变化的 watch 帧 + 新事件”；
- UI 可以随时“冻结”（调用 pause），冻结后仍可查看已有历史。

### 4.2 单步（step）

- 仿真处于暂停；
- 用户选择“下一步（tick）”或“下一步（检查点）”；
- 仿真线程推进到目标，trace 生成 `StepFrame`，再次暂停；
- UI 渲染 before/after + 区间事件。

### 4.3 回放（replay，规划）

- 不启动 SUMO；
- 从 run 目录的 JSONL + `graph.snapshot` + truth 重建 watch 帧；
- 支持时间轴拖动、前进/后退、按检查点跳转；
- **当前未实现**；详细设计见 [07 API 与回放](07-API与回放.md)。

## 5. 线程与并发

```text
仿真线程                          FastAPI 线程 / 协程
────────                          ────────────────────
step_once()
  probes.write()  ──lock──►  TraceStore  ◄──lock──  GET /api/trace/frames
  breakpoint.eval()
  step_controller.wait()  ◄──Condition──  POST /api/trace/step
```

约束：

- **绝不在 `ctx.emit` 内等待用户输入**；否则检测时延被污染，`stop()` 可能卡住；
- Probe 只做轻量投影/拷贝，不做 JSON 序列化大对象；
- SSE 生成器读取 store 的快照，不直接读仿真对象；
- 慢客户端由 store 的 `dropped` 计数和“只发最新帧”策略处理；
- `stop()` 必须能唤醒等待中的 StepController。

## 6. 生命周期

| 事件 | TraceService |
|---|---|
| 会话 start | 创建；注册全局 targets；加载 profile；清空 store |
| 会话 reset | 销毁旧实例，按原参数重新创建 |
| 会话 stop | 保留当前进程内存快照供页面查看；trace.jsonl flush 未实现 |
| 页面晚加入 | 拉取 full snapshot；增量 `since` 未实现 |
| 页面断线重连 | 当前重新拉 full snapshot；`Last-Event-ID` 增量未实现 |
| 仿真 error | 发 `error` 事件；页面显示错误；不阻塞主控制台 |

## 7. 数据流：A1 一次注入

```text
t0 tick:
  scheduler.tick
    └─ AttackProbe: attack.start(A1, rsu=RSU-01, victim=eastbound.2, ghost=3, load=450)
  sensing.tick
    └─ HookProbe: RSU-01.objects before=3 after=6, added=[9000,9001,9002]
    └─ RecordProbe: sensing.objects(RSU-01) → WatchFrame(delta=+3)
    └─ StateProbe: sensor RSU-01 table 更新
  v2x.tick
    └─ RecordProbe: v2x.cpm(RSU-01) object_count=6
  control.tick
    └─ RecordProbe: control.command(ttc=1.481) → WatchFrame(veh:eastbound.2.state)
  after_tick
    └─ StateProbe: pc5 cbr=0.437, offered=570
    └─ DetectorProbe: ghost_object(RSU-01)
    └─ BreakpointController: 命中 S1/S2 → 请求暂停
```

## 8. 失败模式

| 失败 | 行为 |
|---|---|
| trace 关闭 | 零开销；现有功能不变 |
| probe 异常 | 记录一次 trace error，禁用该 probe；仿真继续 |
| store 满 | 按策略淘汰旧帧；`dropped` 递增 |
| 客户端太慢 | SSE 合并中间帧；关键事件保留 |
| 单步超时 | 返回 504/超时；仿真保持暂停或按配置继续 |
| SUMO 异常 | 与现有行为一致；trace 只记录错误 |
| 真值读取被禁用 | `TRUTH` target 不注册；页面不显示 |

## 9. 部署与兼容

- 同进程，不新增端口/服务；
- `/trace` 与 `/` 共用 `MANAGER`；
- 新 API 前缀 `/api/trace/`，不动现有 `/api/stream`；
- CLI/批处理默认不启用 trace；需要时 `--trace`；
- 前端无构建步骤，直接静态文件；
- 旧 run 没有 trace 文件时，回放降级为“从原始流重建”（**规划，未实现**）。

## 10. 备选方案

| 方案 | 结论 |
|---|---|
| 纯前端解析 JSONL | 不可行：实时性差、30+ 条流重建复杂、无法做单步 |
| 前端轮询 `/api/state` 并扩展 | 只能做低频看板；10 Hz 全量快照太重 |
| WebSocket | 可行但没必要；SSE 已满足单向推送 |
| 独立微服务 | 增加部署复杂度；单机 demo 不需要 |
| 直接改主控制台 | 布局冲突；控制/观察职责混在一起 |
