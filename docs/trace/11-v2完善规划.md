# 11 v2 完善规划：从 A1 原型到可扩展追踪

> 状态：**规划稿**，用于拆解 [10 v1 实现说明](10-v1实现说明.md) §9 的下一步建议。  
> 基线：`feature/trace-watch`（v1 原型，36 项 pytest 通过）。  
> 目标：把“能演示 A1 的原型”推进到“可扩展、可复现、可回放”的追踪子系统。  
> 说明：本文只做设计/排期，不改攻击逻辑、检测器规则和真值口径。

## 1. 结论

v1 已经证明三件事：独立 `/trace` 页面可用、watch/trace 数据层可投影、A1 可以按检查点暂停。  
v2 不再继续往 `TraceService` 里堆 A1 细节，而是补四层能力：

```text
框架层：TraceProfile + 声明式检查点     → 新攻击只加 profile
运行层：S0 + 增量 SSE + 单控制者        → 演示可控、重连不抖
复现层：trace.jsonl + 回放 + 导出       → 跑完还能复盘/分享
归因层：HookBus/emit origin + focus     → 说清“谁改了谁”
```

建议按四个版本交付：

| 版本 | 主题 | 对应 §9 建议 | 估算（1 人，含测试） |
|---|---|---|---|
| **v2.0** | 框架抽离 + S0 + Step 详情 | 1、2 + 10 §7 的 Step 详情 | 5–7 人日 |
| **v2.1** | 增量 SSE + 单控制者 | 3、6 的控制部分 | 4–6 人日 |
| **v2.2** | trace.jsonl + 回放 + 导出 | 4 | 6–8 人日 |
| **v2.3** | origin 归因 + focus + A2/A4 样板 | 5、6 的 focus 部分 | 5–7 人日 |
| **v2.4** | 5G 核心网/平台数据融合（comm 已进 master，待 CoreProvider） | 预留项，见 W7 | 5–7 人日 |

总计约 **25–35 人日**，不含 A5–A10 的完整攻击 profile。每个版本都应能单独合并、单独演示，不允许“做了一半不能跑”。

## 2. 现状问题与工作流映射

| §9 建议 | v1 现状 | 直接后果 | 归属 |
|---|---|---|---|
| 1. 抽 `TraceProfile` | S1–S5 的触发、标题、文案、阈值都在 `TraceService` | 加 A2 必须改 service；容易把 A1 语义写死 | **W1** |
| 2. S0 `after_scheduler` 暂停 | `after_scheduler` 只登记攻击，不暂停 | 注入和首条制动常在同一 tick，观众看不到“先注入、后制动” | **W2** |
| 3. SSE 增量 | 每次变化推全量 snapshot（约 10–30 KB） | 10 Hz 下带宽/解析/重绘都浪费；断线只能全量重来 | **W3** |
| 4. `trace.jsonl` + 回放 | 数据只在内存，stop 后只能看当前进程 | 无法复盘、分享、做验收材料 | **W4** |
| 5. HookBus/emit origin | ghost 靠目标列表差异推断；A4 直接 emit 无归因 | “谁注入的”说不清；A4 事件可能挂不到攻击 | **W5** |
| 6. 多攻击 focus + 单控制者 | 所有攻击共用检查点；多浏览器可并发 step | 演示时被别的攻击打断；并发 step 产生竞态 | **W6** |

另外有三项“不修就会持续误导观众”的语义问题，放进 W1 一起处理：

1. **`affected` 过宽且粘滞**：当前 `affected = 收到过 control.command`，普通 ADAS 也会置位；`_commanded` 只在新的攻击启动时清空。应拆成 `commanded` / `affected` / `involved`。
2. **`pc5.rise` 像“异常”**：当前只是相邻帧 CBR +0.1 或 offered +100 的阈值标记，不要求有攻击，也不带基线。应改名为“负载变化”语义，带 baseline/threshold/attack_id，并明确 `derived=true`。
3. **`last_step` 被裁剪**：API 只返回摘要，before/after/events 留在内存。应提供按 `step_id` 查询完整 StepFrame 的接口。

## 3. 目标与非目标

### 3.1 v2 目标

1. **加攻击不改前端**：A2–A10 只需要新增 `profiles/aX.py` 并注册；`/trace` 的 HTML/JS 不改。
2. **单步可解释**：S0 在层执行前暂停；每个 StepFrame 有 `pause_point`、`before/after`、`narrative`、`skipped` 原因。
3. **重连不抖**：SSE 支持 `since`/`Last-Event-ID` 增量；落后太多时用 full snapshot 兜底。
4. **跑完能复盘**：每次 Web run 落 `trace/`，不启动 SUMO 也能回放、拖时间轴、导出 zip。
5. **事件可归因**：hook 修改和直接 emit 都带 `origin`；A4 的 `auth.cert`/`v2x.cam` 能挂到正确攻击。
6. **演示可控**：同一会话只有一个 trace 控制者；并发 step 返回 409，不产生双推进。
7. **不改变仿真**：trace 开关、暂停、单步都不改变 RNG、检测器输入、原始记录和真值。

### 3.2 非目标

- 不做 Python 源码级单步（pdb/`sys.settrace`）、不做 IDA 式反汇编；
- 不做 pcap 级逐包追踪；
- 不在本轮补齐 A5–A10 的完整检查点（只做 A2/A4 作为框架样板；核心网数据接入见 W7，不要求一次做全 A5–A10）；
- 不把 `feature/comm-layer-extension` 的核心网实现直接复制进 trace；只通过只读 provider 接入；
- 不做云端存储、账号体系、多人协作；
- 不为了 trace 去改攻击的注入逻辑（只允许补 `origin` 元数据）；
- 不回写/重写 Git 历史，不处理已移除原始资料的历史 blob。

## 5. 工作流拆解

### W1：TraceProfile 与通用检查点

**目标**：`TraceService` 从“A1 专用控制器”变成“profile 驱动的观察/暂停引擎”。

#### 5.1 接口

```python
class TraceProfile(Protocol):
    id: str
    attack_types: tuple[str, ...]

    def targets(self, inst) -> list[TargetSpec]:
        """该攻击额外需要的 target；全局 target 由 service 注册。"""

    def checkpoints(self, inst) -> list[Checkpoint]:
        """按展示顺序返回检查点；optional=True 的允许不命中。"""

    def narrative(self, stage_id: str, ctx: dict) -> str:
        """一句话讲解；只做白名单字段的 str.format，不执行表达式。"""
```

```python
@dataclass(frozen=True)
class Checkpoint:
    id: str                       # S0/S1/.../END
    title: str
    when: Trigger                 # 声明式触发条件
    pause_at: str = "after_tick"  # after_scheduler / after_tick / after_sensing
    optional: bool = False
    narrative: str = ""           # 支持 {rsu}/{victim}/{ghost_count} 等占位符
    max_wait_s: float | None = None
```

Trigger 第一版只支持：

| 类型 | 用途 | A1 例子 |
|---|---|---|
| `AttackStart` | S0 | 攻击进入 started |
| `FirstRecord` | 首条记录 | `control.command`，`dst=victim` |
| `FirstDelta` | 首个字段变化 | `sensor:<rsu>.objects.ghost_count > 0` |
| `Alert` | 首条告警 | `ghost_object` |
| `Effect` | 物理/链路后果 | `veh:<victim>.state.speed` 在 0.5 s 内下降 ≥0.5 |
| `AttackEnd` | END | `inst.finished` |
| `All` / `Any` | 组合 | S3 的 CBR 或 offered |
| `MaxStep` | 兜底 | 2 s 内无检查点 |

**不允许**：任意 Python 表达式、`eval`、正则来自前端。所有阈值来自 profile 常量或 `AttackSpec.params` 的白名单字段。

#### 5.2 A1 迁移对照

| 阶段 | 新触发 | 暂停点 | 文案要点 |
|---|---|---|---|
| S0 | `AttackStart` | `after_scheduler` | RSU、victim、ghost 数、extra_load；强调“层尚未执行” |
| S1 | `FirstDelta sensor:<rsu>.objects.ghost_count > 0` | `after_tick` | 3→6，新增 9000/9001/9002 |
| S2 | `FirstRecord control.command where dst=victim` | `after_tick` | TTC、decel、src；可选 |
| S3 | `FirstDelta net:pc5` CBR 比基线 +0.1 或 offered +100 | `after_tick` | baseline → current，标注“变化标记，不是检测结论” |
| S4 | `Effect veh:<victim>.state.speed drop≥0.5 / 0.5s` | `after_tick` | 物理后果；可选 |
| S5 | `Alert` 首条 | `after_tick` | rule/entity/latency；S4 未出现时最多等 0.5 s |
| END | `AttackEnd` | `after_tick` | 汇总未命中项 |

S2/S4 仍然允许“不命中”；StepFrame 要带 `skipped: [{id, reason}]`，不能是空白。

#### 5.3 通用引擎

- `TraceService.after_scheduler()`：只做 attack 注册、profile 选择、S0 判断；
- `TraceService.after_tick()`：更新全局 target，交给 `CheckpointEngine.evaluate()`；
- `StepController`：
  - `begin(mode, pause_point)` 记录 `from` 和 before；
  - `finish(checkpoint, events)` 生成 StepFrame，统一处理 `attack_id/stage_id/narrative/effects`；
  - `MAX` 兜底逻辑从 service 移入 controller；
- `TraceStore`：`frames` 按 target 保留最近 1200 帧、`events` 3000 条、`steps` 50 条；提供 `delta(since)`、`frames_at(seq)`、`step(step_id)`；
- `StepFrame` 增加 `pause_point`、`profile_id`、`status`（`hit`/`max_step`/`attack_end`/`error`）、`effects`、`skipped`；
- `/api/trace/step/{step_id}` 返回完整 before/after/events；`/api/trace/state` 仍只返回摘要。

#### 5.4 语义修正

- `veh:fleet` 行增加：
  - `commanded`：收到过 `control.command`；
  - `affected`：有活动攻击 flag，或速度下降超过阈值，或命中 profile 的 effect；
  - `involved`：是某个攻击的 victim/target。
  - 三者都按攻击生命周期清理，不再全局粘滞。
- `pc5.rise` 改名/改语义为“负载变化”：
  - 只在有活动攻击且 `extra_load/jam` 有贡献时产生；
  - `data` 带 `baseline`、`current`、`delta`、`threshold`、`derived=true`；
  - `severity=effect`，不参与检测器统计，也不在 UI 标成 anomaly。
- `ghost.added` 优先从 W5 的 hook origin 产生；目标列表差异只作为 fallback。

#### 5.5 验收

- `TraceService` 中不再出现 `A1`、`S1`–`S5`、`ghost_count` 等攻击专属字符串（grep 检查）；
- A1 在 seed=14 的演示顺序仍为 S0→S1→S2→S3→S4→S5，且每步 before/after 正确；
- 新增一个 `DummyProfile` 测试：只注册 profile，不改 service/front-end，就能产生一个检查点；
- A1 profile 单测覆盖 optional 缺失、MAX 兜底、S2/S4 不命中；
- 36 项旧测试全绿，新增 profile/step 测试。

### W2：S0 与暂停协议

**目标**：在 `scheduler.tick()` 之后、任何层执行之前暂停；S0 能看到“攻击已选目标，但注入尚未发生”。

#### 5.6 关键设计：armed + pause gate

不能在 `ctx.emit` 内暂停，也不能只调用 `sim.pause()` 后继续跑层。推荐两条配合：

1. **armed**：只有显式“开始追踪/等待攻击”时才在 S0 停，避免无攻击时页面莫名暂停。
2. **pause gate**：`after_scheduler` 命中 S0 后，仿真线程在安全边界阻塞等待；API 的 `step/resume/stop` 负责唤醒。

```text
trace.arm(focus)
  → 注入 A1
  → scheduler.tick() 启动攻击
  → trace.after_scheduler(): begin_step() + 生成 S0
  → sim.pause_at("checkpoint:S0")   # 阻塞，层未执行
  → 用户点“下一步”
  → step(): 释放 gate，after_tick() 继续求值 S1...
```

实现约束：

- `Simulation` 增加 `_pause_gate: threading.Condition`；
- `pause_at(reason)`：设置 `state=paused`、`_paused_ack`，然后 `cond.wait()`；
- `resume()` / `step()` / `request_stop()` 必须 `notify_all()`；
- `request_stop()` 后 `pause_at` 返回 `False`，`step_once()` 立即结束本 tick，不再执行剩余层；
- 不允许在 `sumo.step()` 调用中、`ctx.emit()` 内、检测器回调内暂停；
- gate 不设自动超时，避免演示时“自己跑掉”；但 `stop` 必须能打断；
- `TraceService.arm()` 只影响 trace 检查点，不改变仿真状态。

#### 5.7 同 tick 的 S0→S1

S0 和 S1 可能在同一 tick：

- S0 的 `from` 是 scheduler 前，`to` 是 scheduler 后，`pause_point=after_scheduler`；
- 下一步释放 gate，执行各层，`after_tick` 命中 S1；
- StepFrame 的 `t/tick` 可能相同，UI 用 `pause_point` 和“同一 tick · 层前/层后”标签区分；
- 不把 S0 和 S1 合并成一个 StepFrame；合并会丢掉“注入前”的教学价值。

#### 5.8 验收

- S0 时 `sensing.last_objects` 还没有 ghost；目标 RSU 的 `objects` 列表未变；
- 点一次“下一步”后，S1 出现 ghost，且 `from`/`to` 的 seq 正确；
- 无攻击时 `arm` 不会暂停，页面显示“等待攻击”；
- S0 暂停时 `stop` 能在 2 s 内退出，不留下线程；
- tick 单步从 S0 出发只推进一个 tick，然后停在 `step:tick`；
- 单步/连续运行的同 seed 原始记录一致（排除 `t_wall_ns` 和检测时延）。

### W3：增量 SSE 与前端增量应用

**目标**：从“每次变化推全量 snapshot”改为“初始 snapshot + 后续 since 增量”，同时保留全量兜底。

#### 5.9 游标与 delta

`TraceStore` 维护：

- `cursor`：当前最大 seq（frame/event/step 共用）；
- `frame_floor` / `event_floor`：ring buffer 的最老 seq；
- `delta(since, targets=None, limit=100)`：

```json
{
  "schema": "isacsim.trace.delta/1",
  "from": 1800,
  "cursor": 1842,
  "frames": [{"seq": 1830, "target_id": "net:pc5", "...": "..."}],
  "events": [{"seq": 1831, "kind": "alert", "...": "..."}],
  "steps": [{"step_id": "...", "title": "..."}],
  "status": {"state": "paused", "t": 3.1, "tick": 62, "pause_reason": "checkpoint:S1"},
  "dropped": null,
  "reset": false
}
```

规则：

- `frames` 只返回每个 target 在 `since` 之后的最新一帧（允许合并中间帧）；
- `events` 不合并、不丢；超过 `limit` 时截断并带 `dropped.events`，客户端应重新拉；
- `since < floor` 时 `reset=true`，服务端直接给 full snapshot；
- 初始连接发 `event: snapshot`，后续发 `event: delta`；
- SSE 的 `id:` 用 `cursor`，支持浏览器 `Last-Event-ID` 自动重连；
- 5 s 心跳；无变化不发空 delta。

#### 5.10 API

```text
GET /api/trace/stream?since=1842&targets=...&focus=...
GET /api/trace/delta?since=1842&limit=200
GET /api/trace/step/{step_id}
```

兼容：

- `/api/trace/state` 继续返回完整 snapshot，供首屏/调试/旧客户端；
- `/api/trace/stream` 的旧行为可通过 `?format=full` 保留一个版本；
- 新增能力写进 `/api/trace/capabilities`：`delta_stream`、`step_detail`、`replay`。

#### 5.11 前端

- `state.frames` 从“每次替换”改为 `Map` 合并；
- `renderEvents()` 改为“追加 + 去重 + 上限 300”，保留现有 `pointerdown` 委托和 `eventCache`；
- 只更新受影响 target 的卡片，避免整页 `innerHTML` 重建；
- `applyDelta` 与 `applySnapshot` 共用渲染函数；
- 暂停且 cursor 未变时，不重建列表（沿用 v1 的 key 守卫）；
- 断线/`reset` 时清空本地 frames/events，重新应用 snapshot；
- 用 `?delta=0` 作为回退开关，方便灰度和排查。

#### 5.12 验收

- 首屏 1 次 snapshot；之后 1.5 s 内只收到新增事件/帧，不重复；
- 用 `Last-Event-ID` 重连，不重复已见事件，不丢关键事件；
- 人为制造 gap，客户端收到 `reset=true` 并恢复到一致状态；
- 暂停 3 s 只有心跳，DOM 列表不重建；
- 事件详情、表格行详情仍可用（v1 回归）；
- delta 帧平均 < 32 KB，峰值 < 64 KB。

### W4：trace.jsonl、回放与导出

**目标**：run 结束后不依赖 SUMO 和内存，能重新打开、拖时间轴、按步回看、导出。

#### 5.13 落盘格式

每次 Web run 的 `out/web/<run_id>/trace/`：

```text
trace/
├─ meta.json
├─ events.jsonl
├─ watch.jsonl
├─ steps.jsonl
└─ summary.md        # 可选，自动生成的讲解摘要
```

统一行格式：

```json
{"schema":"isacsim.trace.file/1","seq":1842,"type":"event","t":3.10,"tick":62,"payload":{}}
```

- `meta.json`：run_id、scene、seed、duration_s、step_s、trace schema、profile ids、focus、创建时间、限制、是否截断；
- `watch.jsonl`：只写变化帧，保留 `values/delta/status`；
- `events.jsonl`：所有 TraceEvent，不采样；
- `steps.jsonl`：StepFrame 元数据 + `from/to`；完整 before/after 可由 `watch.jsonl` 在回放时重建，也可按配置写入；
- 写入策略：1 s 或 100 行 flush；`stop()` 时 close；写入失败不阻断仿真，meta 记 `trace_write_error`；
- 体积上限：默认 256 MB/run；超过后停止写并标记 `truncated=true`，页面提示“回放不完整”。

#### 5.14 回放后端

- `TraceRun` 打开目录，建立：
  - `events_by_seq`；
  - `frames_by_target`（按 seq 排序，`bisect` 查 `<= seq` 的最新帧）；
  - `steps_by_id`；
- `ReplaySession` 不启动 SUMO、不创建 detector、不做攻击注入；
- API：

```text
GET /api/trace/replay/runs
GET /api/trace/replay/{run_id}/meta
GET /api/trace/replay/{run_id}/state?cursor=...
GET /api/trace/replay/{run_id}/frames?since=...
GET /api/trace/replay/{run_id}/events?after=...
GET /api/trace/replay/{run_id}/steps
```

- 旧 run 没有 `trace/` 时：先返回 `unavailable`，不回退解析原始流（原始流回退放 P3，避免本轮失控）。

#### 5.15 回放前端

- `/trace?run=<id>` 进入只读模式；
- 时间轴可拖拽 seek；上一步/下一步按 StepFrame；播放 0.5×/1×/2×/4×；
- 控制区显示“回放”，禁用注入/暂停/继续；
- 事件详情、Step 详情复用实时模式渲染器；
- 没有 trace 的 run 显示明确空态，不伪装成实时会话。

#### 5.16 导出

- `GET /api/trace/export?run_id=` 返回 zip，包含 `trace/` 和 `summary.md`；
- 复用现有 `SessionManager.download` 的路径校验逻辑；
- `summary.md` 由 steps 的 title/narrative 生成，不引入新的报告系统。

#### 5.17 验收

- 跑一次 A1 → stop → 打开 `?run=`，能看到同样的 S0–S5；
- 回放不启动 SUMO 进程；
- 拖时间轴到任意 seq，frames/events 与落盘记录一致；
- 导出 zip 可解压，`meta.json`/`events.jsonl`/`steps.jsonl` 行数一致；
- 60 s A1 run 的 `trace/` 体积 < 50 MB（目标，不是硬上限）。

### W5：HookBus / emit origin 与归因

**目标**：每个被攻击修改的记录都能回答“哪个攻击、哪个 hook、改了什么”；A4 直接 emit 也能归因。

#### 5.18 数据模型

```python
@dataclass(frozen=True)
class Origin:
    kind: str                 # "hook" | "emit" | "derived"
    attack_id: str | None
    hook: str | None          # "A1:sensing.objects"
    source: str | None        # 原始 source/entity
    changed: tuple[str, ...]  # 顶层字段
```

`TraceEvent` 增加：

```json
{
  "profile_id": "a1",
  "stage_id": "S1",
  "origin": {"kind": "hook", "attack_id": "...", "hook": "A1:sensing.objects",
             "changed": ["objects"]},
  "caused_by": [12]
}
```

`caused_by` 只做“明确可证明”的关联（例如 S1 事件引用 `attack.start` 的 seq）；不做全局因果推断。

#### 5.19 HookBus 改造

- `HookBus.on(stream, fn, *, owner=None, label=None)`；旧调用保持兼容；
- `AttackInstance.hook()` 自动传 `owner=self.id`、`label=f"{atype}:{stream}"`；
- `HookBus.apply_traced()` 返回 `(payload, mutations)`；`apply()` 保留旧签名；
- `ctx.emit(..., origin=None)` 把 origin/mutations 传给 `trace.on_record()`，**不改变 Record 的落盘 schema**；
- 对 `objects` 这类列表，记录 `count_before/count_after`、`added_ids/removed_ids`，不复制整张大表；
- 直接 emit 的 A1–A4 调用补 `origin={"kind":"emit","attack_id":self.id}`。

#### 5.20 消费方式

- `ghost.added` 优先由 `sensing.objects` 的 hook mutation 产生；
- `record.mutated` 事件进入右栏，详情含 before/after 摘要；
- A4 的 `auth.cert`、`auth.fingerprint`、`v2x.cam` 直接 emit 也能带 `attack_id`；
- `pc5.rise`、`control.command`、`speed_drop` 的 `attack_id` 不再只靠 `_attack_for_vehicle` 猜测。

#### 5.21 验收

- A1 的 `ghost.added` 事件 `origin.hook == "A1:sensing.objects"`；
- A4 的克隆/伪造 CAM 事件 `attack_id` 正确；
- 同时跑 A1+A4 时，事件不串攻击；
- 关闭 trace 时 HookBus 不产生额外深拷贝/开销；
- 原始 `*.jsonl` 的 schema 不变，检测器输入不变。

### W6：多攻击 focus 与单控制者

**目标**：演示时只被关注的攻击打断；同一会话只有一个 trace 控制者。

#### 5.22 focus

- `TraceService.focus_attack_id`，默认 `None`（所有攻击）；
- `POST /api/trace/focus {"attack_id": "..."}`；`/trace?focus=...`；
- 只影响“是否按该攻击的检查点暂停”，不影响记录：其他攻击的事件仍进 store；
- StepFrame 按 `attack_id` 分组；同 tick 多攻击命中时合并为一个 StepFrame，`events` 分组显示；
- UI 顶部加“聚焦：全部 / A1 / ATK...”选择器；切换焦点不重启仿真。

#### 5.23 单控制者

- `SessionManager` 增加 `control_owner` 租约：
  - `POST /api/trace/control/claim {client_id}`：首个客户端获得 token；
  - 后续客户端返回 `409` + 当前 owner；
  - token 通过 `X-Trace-Token` 传给 `step/pause/resume/focus`；
  - 租约 15 s，任何控制命令或心跳续期；页面关闭/释放后释放；
- 所有 trace 控制入口先校验 owner；未持有时返回 409：
  ```json
  {"detail": "trace control is owned by another client", "code": "control_owned", "owner": "..."}
  ```
- 主控制台的“紧急停止/复位”不受租约限制（安全阀），但要在 UI 提示“会中断追踪控制者”；
- `Simulation.step()` 内部再加一个非阻塞 `_step_lock`，即使 API 校验漏掉也不会双推进。

#### 5.24 验收

- 两个浏览器同时点“下一步”，只有一个成功，另一个收到 409，不出现双 tick；
- 控制者关闭后 15 s 内可被接管；
- 设置 focus 后，非焦点攻击的检查点不暂停，但其事件仍可查；
- 取消 focus 后恢复全攻击检查点；
- 主控制台停止仍能立即生效。

所以：**如果按现在的 v2.0 直接开工、之后再合 comm 分支，需要回头改 `TraceService`、target 注册、事件映射和暂停点**。这不是“完全没考虑”，但还没有达到“融合不需要返工”的程度。

#### 5.25 分支现状（合并前记录）

`feature/comm-layer-extension` 从 `d045fe1` 分出，已包含：

- `CoreLayer` + AMF/SMF/UPF/NEF/UDM/AUSF，`core.nas`/`core.session`/`core.qos`/`core.upf`/`core.nef`/`core.handover` 流；
- `PlatformLayer`，`app.auth`/`app.ingest`/`app.subscription`/`app.control`/`app.audit` 流；
- `defense.action`、`detect/chain.py`、`health.py`；
- `Simulation.snapshot()` 的 `core`/`platform`，以及 `/api/core`、`/api/platform`；

它没有 watch/trace 页面，也没有 `isacsim.trace` 包。两个分支都改了 `core/context.py` 和 `core/engine.py`；comm 另外改了 `core/records.py`、`isacsim/__init__.py`（record/2），trace 另外新增了 `isacsim/trace/` 并改了 `web/api.py`、`web/session.py`。直接合并会有冲突。

#### 5.26 命名冲突（PR-0，已完成）

> 已按本节执行：comm 侧 `Trace` → `SpanContext`、`TraceFactory` → `SpanFactory`，`ctx.trace` → `ctx.span`；`record.trace_id/span_id` 保持不变。合并后的 `SimContext` 同时保留 `trace`（`TraceService`）与 `span`（分布式链路）。以下保留为背景记录。

comm 分支的 `Trace` 是“分布式链路 ID”，trace 分支的 `TraceService` 是“观测追踪”，两者不能共用 `ctx.trace`：

| 符号 | comm 分支 | trace 分支 | 冲突 |
|---|---|---|---|
| `SimContext.trace` | `Trace`（span 上下文） | `TraceService` | 同名字段，语义不同 |
| `Trace` / `TraceFactory` | 分布式 ID 生成 | 观测追踪 | 类型名重载 |
| `ctx.emit(..., trace=...)` | 传 span 上下文 | 无 | 合并后参数歧义 |
| `Record.trace_id` | 分布式链路 | 无 | **保留**，不要改名 |
| `Simulation.trace` | 无 | `TraceService` | 可保留，但文档要写清 |

推荐在合并前做一次小重构：

1. comm 分支 `Trace` → `SpanContext`，`TraceFactory` → `SpanFactory`；
2. `ctx.trace` → `ctx.span`，`ctx.emit(trace=...)` → `ctx.emit(span=...)`；
3. `record.trace_id/span_id/parent_span_id/chain_id` **保持不变**，它们描述分布式链路，不是 `/trace` 页面；
4. watch 侧继续叫 `TraceService`，文档统一称“**观测追踪（watch trace）**”，comm 侧称“**分布式链路（span trace）**”；
5. `TraceEvent` 不再新增 `trace_id` 字段，改用 `correlation_id` / `chain_id` 关联分布式链路，避免再次混淆。

这一步应作为 **PR-0** 先做；如果 comm 分支暂不合并，也建议先在 trace 分支把命名边界定下来。

#### 5.27 接入层次：WatchProvider ≠ TraceProfile

核心网节点状态是**全局域数据**，不应该只在 A5 profile 里出现；否则没有攻击时 `/trace` 看不到核心网，A6/A7/A9 还要重复注册。

建议在 W1 增加 `WatchProvider`（域采集器），与 `TraceProfile`（攻击剧本）分开：

```python
class WatchProvider(Protocol):
    id: str
    def targets(self) -> list[TargetSpec]: ...
    def poll(self, ctx) -> list[FrameUpdate]: ...
```

- `TraceService` 组合 `SensorProvider`/`FleetProvider`/`Pc5Provider`/`DetectorProvider`（把 v1 的全局 target 也迁进来）；
- `CoreProvider` 读 `sim.core.snapshot()`；
- `PlatformProvider` 读 `sim.platform.snapshot()`；
- `A5Profile`/`A6Profile` 只声明 checkpoint/narrative，不拥有全局 core target；
- 无攻击时 `CoreProvider` 仍注册 target、仍更新帧；`scene.core.enabled=False` 时给 `disabled` 状态而不是报错。

#### 5.28 建议的 core/platform target

| target | kind | 来源 | 关键字段 |
|---|---|---|---|
| `core:summary` | struct | `sim.core.snapshot()` | enabled、attached、registered、sessions、flows、bus_pending |
| `core:gnb` | struct | `core.gnb` | entity、attached、health.status/reasons/metrics |
| `core:amf` | struct | `core.amf` | received/rejected/dropped、queue_depth、registered、handovers、health |
| `core:smf` | struct | `core.smf` | sessions、degraded_sessions、rejected、health |
| `core:upf` | struct | `core.upf` | flows、teids、route、route_override、health |
| `core:nef` | struct | `core.nef` | tokens、subscriptions、unsubscribed、revoked、health |
| `core:udm` | struct | `core.udm` | subscribers、barred、health |
| `core:ausf` | struct | `core.ausf` | vectors_issued、rejected、health |
| `core:dn` | struct | `core.dn` | route、health |
| `core:ues` | table | `core.amf.ues` | ue_id、gnb_id、state、pdu_session_id（最多 40） |
| `core:sessions` | table | `core.smf.sessions` | session_id、ue_id、dnn、upf_id、ue_ip、5qi、state（最多 40） |
| `core:flows` | table | `core.upf.flows` | flow_id、ue_id、session_id、teid、qfi、route、state（最多 40） |
| `platform:summary` | struct | `sim.platform.snapshot()` | enabled、tenant、qps、ingest/iam/subscriptions/dispatcher/audit、health |
| `platform:tokens` | table | `platform.iam` | token_id、subject、tenant、scopes、expires、revoked（最多 40） |
| `platform:subscriptions` | table | `platform.subscriptions` | sub_id、tenant、event_types、state（最多 40） |
| `det:chains` | table | `detector.snapshot().chains` | chain_id、root_cause、nodes、confidence |
| `defense:actions` | table/event | `stats.defense_actions` | action、target、result、latency_ms |

注意：

- `core:amf` 等是“节点 + 计数 + 健康”的结构，不要拆成一堆 scalar target；
- `health` 是派生值，`fields` 里标 `derived=true`；它来自观测，不是 truth；
- 当前 `CoreLayer.snapshot()` 的 SMF/UPF 只有计数，没有 `sessions/flows` 列表。建议在 `CoreLayer.snapshot()` 增加**有界**的 `sessions[:40]`、`flows[:40]`，而不是让 trace 直接抓 `sim.core.smf.sessions` 私有字典；`PlatformLayer.snapshot()` 同理增加 tokens/subscriptions 摘要；
- 表目标统一 `max_rows=40`，超出带 `truncated=true`。

#### 5.29 事件映射与聚合

`core.*`/`app.*` 不能继续靠 `on_record()` 里的几个 `if`，应由 profile 或 provider 声明：

```python
StreamSpec(
    stream="core.nas",
    kind="core.nas",
    target="core:amf",
    summary="{msg_type} {result} @ {entity}",
    severity="effect",
)
```

建议映射：

| 流 | trace kind | 默认 target |
|---|---|---|
| `core.nas` | `core.nas` | `core:amf` |
| `core.session` | `core.session` | `core:smf` |
| `core.qos` | `core.qos` | `core:smf` / `core:upf` |
| `core.upf` | `core.upf` | `core:upf` |
| `core.handover` | `core.handover` | `core:gnb` |
| `core.nef` | `core.nef` | `core:nef` |
| `app.auth` | `app.auth` | `platform:summary` |
| `app.ingest` | `app.ingest` | `platform:summary` |
| `app.subscription` | `app.subscription` | `platform:subscriptions` |
| `app.control` | `app.control` | `platform:summary` |
| `app.audit` | `app.audit` | `platform:summary` |
| `defense.action` | `defense.action` | `defense:actions` |

**A5 的量级必须先处理**：`A5` 在 `tick()` 里最多每秒发约 2000 条 `core.nas`（`rate=200+1800×amplitude`，每 0.1 s 最多 50 条），v1 的 3000 条事件 ring 会在约 2 s 内被 bot 注册刷满，把 A1/A4 的关键事件挤掉。建议：

- 按 `(stream, msg_type, result, cause)` 做 100 ms 聚合，事件里带 `count`、`first_seq`、`last_seq`；
- `registration_reject`、`route_change`、`token_revoke`、`unsubscribe`、`defense.action` 等关键事件首条必留；
- 每个 kind 有配额，超出记 `dropped`，不能静默丢；
- SSE delta 对 core 事件也做批量，不逐条推。

#### 5.30 暂停点：增加 after_layer

comm 分支的层序是：

```text
scheduler → sensing → v2x → uu → core → auth → platform → control → task → edge
```

A5/A6/A7 的关键状态发生在 `core.tick()` 或 `platform.tick()` 内。如果只有 `after_tick`，S1 的“AMF 拒绝/过载”、S2 的“会话失败”、S3 的“平台 ingest”会挤在同一帧。建议 W2 一次性加入通用层边界：

```python
trace.after_layer("core", ctx)
trace.after_layer("platform", ctx)
```

- 只在层函数返回后调用，不在 `ctx.emit()` 内；
- `Checkpoint.pause_at` 支持 `after_layer:core` / `after_layer:platform`；
- 没有匹配检查点时立即返回，不增加暂停；
- `core/platform` 未启用时是 no-op；
- v2.0 可以先只实现 `after_scheduler`/`after_tick`，但**接口要预留 `after_layer`**，避免 W7 再改 `step_once()`。

A5 的示例检查点可以是：

| 阶段 | 触发 | 暂停点 |
|---|---|---|
| S0 | `attack.start` | `after_scheduler` |
| S1 | 首条 `core.nas` reject / `amf_overload` | `after_layer:core` |
| S2 | 首条 `core.session` reject | `after_layer:core` |
| S3 | `app.ingest` 延迟/`app.control` | `after_layer:platform` |
| S4 | `control.command` 或速度下降 | `after_tick` |
| S5 | 首条告警/链 | `after_tick` |

A5–A10 类似，但具体阶段由 `profiles/a5.py` 等决定，service 不写死。

## 8. 性能与资源预算

| 指标 | 目标 | 测量方式 |
|---|---|---|
| trace 开销 | <5% 墙钟（60 s A1） | trace off/on 各 3 次取中位数 |
| 内存 | <100 MB/60 s | `tracemalloc` 或进程 RSS |
| SSE delta | 平均 <32 KB，峰值 <64 KB | 抓包/日志统计 |
| 事件保留 | 3000 条 | store 上限 |
| 每 target 帧 | 1200 帧 | ring buffer |
| Step 保留 | 50 个 | ring buffer |
| trace 文件 | <50 MB/60 s（目标） | `du` |
| 回放打开 | <2 s（50 MB 内） | API 计时 |
| Core 事件 | A5 峰值 2000/s 时有界 | 聚合后事件数/秒 + dropped |
| Core 帧 | 10 Hz，单表 ≤40 行 | target 帧统计 |

超过预算时的降级顺序：先合并 watch 帧，再丢中间帧，最后才丢事件；事件永不静默丢，必须发 `dropped`。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| S0 gate 死锁 | 仿真线程卡住，stop 无效 | Condition + stop notify；T4；gate 只在安全边界 |
| S0/S1 同 tick 观感混乱 | 观众以为没推进 | `pause_point` + UI “同一 tick · 层前/层后” |
| 增量 SSE 引入前端回归 | 点击/详情再次失效 | 保留 full snapshot；`?delta=0`；Playwright T13 |
| trace 文件过大/IO 抖动 | 影响实时性 | 缓冲写、上限、truncated 标记、异步写可后置 |
| origin 深拷贝开销 | 影响 10 Hz 性能 | 只对 trace 开启；列表记录 count/ids；基准 T14 |
| profile DSL 过度设计 | 开发慢、难维护 | 第一版只做 8 种 Trigger，不做表达式 |
| 租约过期/抢占 | 演示中控制权丢失 | 15 s 续期、显式 release、UI 提示、紧急停止不受限 |
| core 事件洪泛 | A5 把 ring 刷满，A1/A4 关键事件被挤掉 | 按 kind/窗口聚合、关键事件必留、配额/dropped |
| `Trace` 命名冲突 | 合并 comm 后 `ctx.trace` 二义 | PR-0 改 `SpanContext`/`ctx.span`，保留 `record.trace_id` |
| 先 trace 后 comm 的合并顺序 | 大面积冲突、重复返工 | comm 先合 master，trace rebase；或 integration 分支 |
| 当前工作区有未提交修改 | 混入无关变更 | 开工前单独分支/PR；每个 W 独立提交 |

## 10. 建议的 PR 拆分与顺序

1. **PR-0 `trace/naming`**：comm 侧 `Trace`→`SpanContext`、`ctx.trace`→`ctx.span`；保留 `record.trace_id`。这是 W7 的前置，也可独立先做。
2. **PR-1 `trace/profile`**：`models.py` + `profile.py` + `checkpoints.py` + A1 profile + `WatchProvider` 接口 + 旧测试适配；不改 API。
3. **PR-2 `trace/s0`**：`pause_gate` + `arm` + S0 + `after_layer` 预留 + Step 详情接口；补 T3/T4/T5。
4. **PR-3 `trace/delta`**：`TraceStore.delta` + SSE 增量 + 前端 applyDelta；保留 full 作为回退；补 T6/T13。

## 11. 待确认的决策

以下按推荐值先写入规划，开工前可调整：

1. **S0 是否自动暂停**：推荐“仅 armed 时自动停”，避免无攻击时页面突然停住。
2. **回放数据源**：推荐先只读 `trace/`，旧 run 标 `unavailable`；原始流回退放后续。
3. **schema**：推荐 additive，不升 `trace/2`；只有改义才升 major。
4. **A2/A4 范围**：推荐本轮只做“能证明框架”的 4–5 个检查点，不追求 A5–A10 全覆盖。
5. **核心网接入层次**：推荐 `CoreProvider` 作为全局 provider，A5–A10 profile 只加检查点；不要把 core 目标塞进某个攻击 profile。
6. **命名**：推荐 comm 侧 `Trace`→`SpanContext`、`ctx.trace`→`ctx.span`；`record.trace_id` 保持不变；watch 侧继续叫 `TraceService`。
7. **合并顺序**：推荐 comm 先合 master，再 rebase trace；如果 comm 暂不合，先完成 PR-0/PR-1 的 provider 接口预留，避免 W7 返工。
8. **单控制者租约**：推荐 15 s；主控制台保留紧急停止/复位。
9. **truth 卡片**：推荐继续不做，等回放稳定后再加“仅演示”命名空间。
