# 09 A1 试点与实施路线

## 1. 为什么先做 A1

A1 是最适合验证 trace 框架的剧本：

- 跨层完整：感知目标列表 → ADAS → 制动 → 信道；
- 数据类型全：表（objects）、结构体（vehicle/channel）、事件（command/alert）；
- 对照强：3 个 RSU 中只有目标 RSU 被改，天然适合“寄存器矩阵”；
- 已有代码走读：[A1 攻击实现解析](../09-A1攻击实现解析.md)；
- 已知缺口明确：目标选择、`ctx.extras`、`flags`、`sensing.frame.object_count`。

A1 跑通后，A2/A3/A4 主要是“换 profile”，不需要重做前端。

## 2. A1 的 watch 目标

| Target ID | 类型 | 数据源 | 说明 |
|---|---|---|---|
| `scene:summary` | struct | `snapshot` | 车辆数、仿真时间、状态 |
| `sensor:RSU-01.objects` | table | `sensing.objects`（post-hook） | 目标 RSU；ghost 高亮 |
| `sensor:RSU-02.objects` | table | 同上 | 对照 |
| `sensor:RSU-03.objects` | table | 同上 | 对照 |
| `sensor:GNB-01.objects` | table | 同上 | 可选折叠 |
| `veh:<victim>.state` | struct | `snapshot.vehicles` + `control.command` | 速度、TTC、指令、flags |
| `veh:fleet` | table | `snapshot.vehicles` + command | 只显示受影响 |
| `net:pc5` | struct | `V2XLayer` / `link.metrics` | offered/CBR/PER/delay/DCC |
| `det:alerts` | event | `detector.snapshot` | 规则/实体/detail/latency |
| `atk:ATK001` | struct | `AttackInstance` | type/t0/t1/rsu/victim/ghost/load |
| `truth:EVT-...` | struct | `TruthStore` | 可选，演示命名空间 |

### 2.1 字段建议

`sensor:<id>.objects`：

```text
frame_seq, object_count, ghost_count
rows[]: object_id, cls, x, y, vx, vy, entity, ghost, source_kind
delta: added/removed/changed by object_id
```

`veh:<victim>.state`：

```text
id, x, y, speed, heading, flags
ttc, last_command{seq, decel, reason, t}
speed_delta_1s, affected_by
```

`net:pc5`：

```text
offered_msgs_s, cbr, per, delay_p50_ms, dcc_factor, jam
extra_load (derived: offered - baseline)
```

`atk:ATK001`：

```text
type, t0, t1, amplitude, rsu, victim, ghost_count, extra_load, status
```

> 当前 `AttackInstance.snapshot()` 没有 `rsu/victim/ghost_count/extra_load`，需要 AttackProbe 读实例字段或补 snapshot；真值里有这些值，但不应让前端依赖 truth。

## 3. A1 检查点

### S0 选目标与参数

- 触发：`attack.start`（建议在 `after_scheduler` 安全点暂停，此时尚未注入）
- before：无
- after：`rsu=RSU-01`, `victim=eastbound.2`, `ghost_count=3`, `extra_load=450`
- 讲解：稳定哈希选中目标 RSU 与受害车；注意“选车没检查装备/覆盖”。

### S1 目标列表被篡改

- 触发：首帧 `sensing.objects` 含 `ghost:*`
- before：`object_count=3`
- after：`object_count=6`, `ghost_count=3`, added `9000/9001/9002`
- 讲解：只改 RSU-01；RSU-02/03 不变；雷达回波/点迹没有 ghost。
- 注意：S1 与 S2 在 seed=14 的 t0 同一 tick；v1 可合并 StepFrame，v1.1 用 `after_sensing` 拆开。

### S2 ADAS 误判

- 触发：首条 `control.command`，`reason=ttc`
- before：`veh:eastbound.2.state` 的 `ttc=null`
- after：`ttc=1.481`, `decel=3.0`, `seq=1`
- 讲解：22 m / 14.857 m/s = 1.481 s < 2.5 s；指令看起来完全合法。
- 注意：若 S1 未拆分，本步与 S1 合并在同一帧。
- 可选：如果未命中，显示“该 victim 未装备/未被目标 RSU 服务”。

### S3 通信负载上升

- 触发：`net:pc5.offered` 较基线 +100，或 CBR +0.1
- before：`offered=120`, `cbr=0.092`
- after：`offered=570`, `cbr=0.437`, `per=0.01`, `delay=5.76`
- 讲解：`extra_load=450` 是抽象 offered load，不是 450 条报文；伪造 DENM 只有 2 Hz。
- 可选：`cbr_spike` 需要 CBR>0.7；短场景不触发。

### S4 物理后果

- 触发：`veh:eastbound.2.state` 的 `speed` 较前 0.5 s 下降 >0.5 m/s
- before：14.86
- after：12.32（1 s 后）
- 讲解：`slow_down` 真的改了 SUMO 速度；其他东向车辆后续也会被幽灵触发。

### S5 检测证据

- 触发：首条 `ghost_object` / `cbr_spike` / `link_degraded`
- after：`ghost_object @ rsu:RSU-01`, detail `(50.477,-8.0,obstacle)`
- 讲解：检测器不读真值；car 类 ghost 不被该规则命中；短场景只有 ghost_object。

## 4. 演示脚本（约 2 分钟）

```text
0:00  打开 /trace，无攻击：展示 3 RSU 目标列表、PC5 正常
0:15  注入 A1（a=0.6, 10 s, start=3）
0:20  S0 自动暂停：看选中的 RSU/victim/ghost/load
0:30  S1：RSU-01 3→6；RSU-02/03 不变；雷达无 ghost
0:50  S2：TTC 1.481、control.command、合法 ADAS
1:05  S3：offered/CBR 上升；解释 450 不是报文数
1:20  S4：车速 14.86→12.32
1:35  S5：ghost_object；解释检测证据
1:50  继续到结束，导出 trace
```

## 5. 必须先补的字段/行为

这些是实施 P1 前要解决的后端小问题：

| 问题 | 影响 | 建议 |
|---|---|---|
| `AttackInstance.snapshot()` 缺计算字段 | `atk:A1` 卡片不完整 | 增加 `rsu_id/victim/ghost_count/extra_load` 或由 AttackProbe 读取 |
| `flags` 只标 victim | fleet 看不到其他受影响车 | 从 `control.command`/速度差派生 `affected_by` |
| `ctx.extras` 每 tick 重建 | A1 的 ADAS DENM/CAM 丢失 | trace 以 `control.command`/speed 为准；不在文档/UI 承诺 DENM |
| Web run 无 `alerts.jsonl` | 回放缺告警 | 在线 DetectorProbe 记录；或停止时 dump |
| `sensing.frame.object_count` 不含 ghost | 帧与对象表不一致 | 页面以 `objects` 为准；frame 标明 |
| A1 目标选择不检查装备/覆盖 | S2 可能不命中 | profile 将 S2 标为 optional；页面显示原因 |
| `HookBus` 无 owner、`ctx.emit` 无 origin | A1 hook diff 能采，但归因不精确；A4 直接 emit 更难 | 给 hook/emit 加 origin；A1 P1 可先用 attack_id 包一层 |

## 6. 分期

### P0：只读实时 watch（不依赖单步）

范围：

- `/trace` 页面骨架；
- `WatchRegistry` 全局目标（sensors/fleet/PC5/DET）；
- 10 Hz watch SSE；
- 冻结/继续；
- 无攻击正常态；
- A1 的 `atk` 卡片（先只读现有字段）。

验收：无攻击 30 s 可视；A1 注入后能看到 RSU-01 变化；开销 <3%。

### P1：A1 profile + trace 事件 + diff

范围：

- A1 `TraceProfile`；
- HookProbe/RecordProbe/StateProbe；
- before/after、ghost 标记、affected 车辆；
- Trace/Xref 右栏；
- S0–S5 检查点的“只读高亮”（不暂停）。

验收：能手动暂停在任意时间，讲清 A1；A2 可复制 profile。

### P2：StepController + 检查点暂停

范围：

- Condition/ack；
- `POST /api/trace/step`；
- StepFrame；
- 自动暂停/下一步/继续；
- 多攻击 focus。

验收：5–6 步讲完；单步与连续记录一致；无竞态。

### P3：回放/导出

范围：

- `ReplayIndex`；
- `/trace?run=...`；
- 前进/后退/拖动；
- 导出 trace/zip/summary。

验收：60 s A1 run 可离线回放；缺 alerts 降级。

### P4：A2–A4，再 A5–A10

- 每个攻击加一个 profile；
- 复用表格/结构体/事件渲染；
- 不需要改 `trace.html/js` 的核心。

## 7. 工作量粗估

| 阶段 | 内容 | 粗估 |
|---|---|---:|
| P0 | 页面 + 全局 watch + SSE + 冻结 | 2–3 人日 |
| P1 | A1 profile + probes + diff + xref | 3–4 人日 |
| P2 | 单步/断点/StepFrame | 2–3 人日 |
| P3 | 回放/导出/降级 | 2–3 人日 |
| P4 | 每个攻击 profile | 0.5–1 人日/个 |

不含 UI 打磨和大规模性能调优。实际取决于是否复用现有 CSS/脚本、是否需要补 snapshot 字段。

## 8. 风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 目标选择导致 S2 不命中 | 高 | 演示尴尬 | profile optional；页面显示原因；可换 seed |
| `ctx.extras` 导致“制动→DENM”讲不通 | 高 | 预期落空 | 文档/页面明确；用 control.command/speed |
| 10 Hz 全量数据太大 | 中 | 卡顿 | 只订阅 10 target；合并 |
| 多客户端抢控制 | 中 | 状态乱 | 单控制者 |
| 无鉴权 | 中 | 暴露 | token/网段 |
| 旧 run 缺 alerts | 中 | 回放不完整 | 在线记录；缺数据标注 |
| UI 过度设计 | 中 | 讲解效果差 | 以 StepFrame 为中心，少装饰 |

## 9. 完成定义（DoD）

P2 完成时，应能：

- 打开 `/trace`，无攻击也能看；
- 注入 A1，自动停在 S0；
- 连续点“下一步”走完 S1–S5；
- 每步都能看到 before/after、事件、影响车辆；
- S2 不命中时，页面明确说明“victim 未装备/未覆盖”；
- 不读真值也能完成讲解（truth 仅辅助）；
- 同 seed 单步 vs 连续记录一致；
- trace 关闭时主控制台/批处理无变化；
- 文档/快捷键/错误提示齐全。

## 10. 不建议在 v1 做

- 源码行级单步；
- 十六进制内存 dump 为主；
- 多人协作/权限；
- 云端 trace 存储；
- 任意表达式断点；
- 全量 18 类流上屏；
- 实时倒带；
- 自动生成视频。
