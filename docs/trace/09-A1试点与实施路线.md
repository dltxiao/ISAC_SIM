# 09 A1 试点与实施路线

> **当前状态（2026-10-30）**：A1 的 S1–S5 与 A5 的 S0–S5 已实现；A1 **没有 S0**；A2–A4、A6–A10 profile 未实现；回放/导出未实现。
> 本文保留 A1 试点设计；现状与差异见 [12 当前实现状态](12-当前实现状态.md)。

## 1. 为什么先做 A1

A1 是最适合验证 trace 框架的剧本：

- 跨层完整：感知目标列表 → ADAS → 制动 → 信道；
- 数据类型全：表（objects）、结构体（vehicle/channel）、事件（command/alert）；
- 对照强：3 个 RSU 中只有目标 RSU 被改，天然适合“寄存器矩阵”；
- 已有代码走读：[A1 攻击实现解析](../09-A1攻击实现解析.md)；
- 已知缺口明确：目标选择、`ctx.extras`、`flags`、`sensing.frame.object_count`。

A1 跑通后，A2/A3/A4 主要是“换 profile”，不需要重做前端。

## 2. A1 的 watch 目标

| Target ID | 类型 | 数据源 | 说明 |
|---|---|---|---|
| `scene:summary` | struct | `snapshot` | 车辆数、仿真时间、状态 |
| `sensor:RSU-01.objects` | table | `sensing.objects`（post-hook） | 目标 RSU；ghost 高亮 |
| `sensor:RSU-02.objects` | table | 同上 | 对照 |
| `sensor:RSU-03.objects` | table | 同上 | 对照 |

| `det:alerts` | event | `detector.snapshot` | 规则/实体/detail/latency |

| `truth:EVT-...` | struct | `TruthStore` | 可选，演示命名空间 |

### 2.1 字段建议

`sensor:<id>.objects`：

```text
frame_seq, object_count, ghost_count
rows[]: object_id, cls, x, y, vx, vy, entity, ghost, source_kind
delta: added/removed/changed by object_id
```

`veh:<victim>.state`：

```text
id, x, y, speed, heading, flags
ttc, last_command{seq, decel, reason, t}
speed_delta_1s, affected_by
```

`net:pc5`：

```text
offered_msgs_s, cbr, per, delay_p50_ms, dcc_factor, jam
extra_load (derived: offered - baseline)
```

`atk:ATK001`：

```text
type, t0, t1, amplitude, rsu, victim, ghost_count, extra_load, status
```

> 当前 `AttackInstance.snapshot()` 没有 `rsu/victim/ghost_count/extra_load`，需要 AttackProbe 读实例字段或补 snapshot；真值里有这些值，但不应让前端依赖 truth。

## 3. A1 检查点

### S0 选目标与参数（A1 未实现；A5 才有 S0）

- 触发：`attack.start`（A5 在 `after_scheduler` 暂停；A1 没有这一步）
- 讲解：稳定哈希选中目标 RSU 与受害车；注意“选车没检查装备/覆盖”。

### S1 目标列表被篡改

- 触发：首帧 `sensing.objects` 含 `ghost:*`
- before：`object_count=3`
- after：`object_count=6`, `ghost_count=3`, added `9000/9001/9002`
- 讲解：只改 RSU-01；RSU-02/03 不变；雷达回波/点迹没有 ghost。
- 注意：S1 与 S2 在 seed=14 的 t0 同一 tick；当前 A1 都在 `after_tick`，S1/S2 会分成两步但同一 tick；`after_sensing` 拆分仍是规划。

### S2 ADAS 误判

- 触发：首条 `control.command`，`reason=ttc`
- before：`veh:eastbound.2.state` 的 `ttc=null`
- after：`ttc=1.481`, `decel=3.0`, `seq=1`
- 讲解：22 m / 14.857 m/s = 1.481 s < 2.5 s；指令看起来完全合法。
- 注意：若 S1 未拆分，本步与 S1 合并在同一帧。
- 可选：如果未命中，显示“该 victim 未装备/未被目标 RSU 服务”。

### S3 通信负载上升

- 触发：`net:pc5.offered` 较基线 +100，或 CBR +0.1
- before：`offered=120`, `cbr=0.092`
- after：`offered=570`, `cbr=0.437`, `per=0.01`, `delay=5.76`
- 讲解：`extra_load=450` 是抽象 offered load，不是 450 条报文；伪造 DENM 只有 2 Hz。
- 可选：`cbr_spike` 需要 CBR>0.7；短场景不触发。

### S4 物理后果

- 触发：`veh:eastbound.2.state` 的 `speed` 较前 0.5 s 下降 >0.5 m/s
- before：14.86
- after：12.32（1 s 后）
- 讲解：`slow_down` 真的改了 SUMO 速度；其他东向车辆后续也会被幽灵触发。

### S5 检测证据

- 触发：首条 `ghost_object` / `cbr_spike` / `link_degraded`
- after：`ghost_object @ rsu:RSU-01`, detail `(50.477,-8.0,obstacle)`
- 讲解：检测器不读真值；car 类 ghost 不被该规则命中；短场景只有 ghost_object。

| 目标选择导致 S2 不命中 | 高 | 演示尴尬 | profile optional；页面显示原因；可换 seed |

## 10. 不建议在 v1 做

- 源码行级单步；
- 十六进制内存 dump 为主；
- 多人协作/权限；
- 云端 trace 存储；
- 任意表达式断点；
- 全量 30+ 条流上屏；
- 实时倒带；
- 自动生成视频。
