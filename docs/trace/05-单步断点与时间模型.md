# 05 单步断点与时间模型

> **当前状态（2026-10-30）**：`Simulation.pause_at()`（Condition）与 `after_scheduler`/`after_layer:core|platform`/`after_tick` 已实现；A5 使用 S0、S1/S2、S3 三档边界，A1 仍只在 `after_tick`。
> focus、单控制者、暂停确认（独立 `control_owner`）未实现。差异见 [12 当前实现状态](12-当前实现状态.md)。

## 1. 三个时间概念

| 概念 | 定义 | 例子 |
|---|---|---|
| tick | 仿真步，默认 50 ms | `t=3.10, tick=62` |
| checkpoint | 攻击链上的语义点，不等于 tick | “首次出现幽灵”“首条 TTC 制动” |
| step | 从当前暂停点推进到下一个断点 | `S1 → S2` |

**演示用的是 checkpoint，不是 1200 个 tick。** tick 单步只作为调试高级选项。

## 2. 运行模式

```text
                 ┌─────────────┐
                 │    idle     │
                 └──────┬──────┘
                        │ start
                 ┌──────▼──────┐
        ┌───────►│    live     │◄───────┐
        │        └──────┬──────┘        │
        │               │ pause         │ resume
        │        ┌──────▼──────┐        │
        │        │   paused    │────────┘
        │        └──────┬──────┘
        │               │ step(tick|checkpoint)
        │        ┌──────▼──────┐
        └────────│  stepping   │
                 └──────┬──────┘
                        │ hit breakpoint
                 ┌──────▼──────┐
                 │   paused    │
                 └─────────────┘
```

另外有 `replay` 模式，不启动 SUMO，状态机是 `paused/playing/scrubbing`，与 live 分开。

## 3. 断点类型

### 3.1 时间

```json
{"type": "time", "at": 3.0, "relative_to": "t0"}
```

用于“攻击开始/结束”“t0+1 s 注入制动”等确定时间点。

### 3.2 阶段

```json
{"type": "stage", "stage_id": "S2", "edge": "enter"}
```

需要 profile/攻击实例提供阶段事件。当前 A1 的 `truth.stages` 是计划，不是运行时事件；短期可用时间/记录触发，长期再让剧本显式发 stage。

### 3.3 首次记录

```json
{"type": "first_record", "stream": "sensing.objects",
 "where": {"sensor_id": "$rsu"}, "predicate": "ghost_added"}
```

用于“首次注入”“首条 DENM”“首条 CAM 位置跳变”。

### 3.4 首次变化

```json
{"type": "first_delta", "target_id": "sensor:$rsu.objects",
 "field": "ghost_count", "op": ">", "value": 0}
```

比解析原始记录更通用；适合 A2/A3/A4 的字段级变化。

### 3.5 告警

```json
{"type": "alert", "rule": "ghost_object", "entity": "rsu:$rsu"}
```

用于“检测器第一次看到”。

### 3.6 效果

```json
{"type": "effect", "target_id": "veh:$victim.state",
 "field": "speed", "op": "drop", "value": 0.5, "window_s": 0.5}
```

用于“车辆真的减速”，避免只看指令不看结果。

### 3.7 组合

```json
{"type": "all", "of": [
  {"type": "stage", "stage_id": "S1"},
  {"type": "first_delta", "target_id": "sensor:$rsu.objects"}
]}
```

只支持 `all/any`，不做任意表达式求值；避免安全/可复现性问题。

## 4. 暂停协议

### 4.1 当前实现

- `pause()`：设置 `_paused`，run loop 在安全边界看到后等待；用于 A1 的 tick 末尾暂停；
- `pause_at(reason)`：设置 `_paused` + `_paused_ack`，然后用 `threading.Condition` **阻塞仿真线程**，用于 A5 的 S0/S1/S2/S3；
- `resume()` / `step()` / `request_stop()` 都 `notify_all()`，唤醒 `pause_at`；
- `step()` 等“本次 step 完成 + 再次暂停”后返回；
- `state=paused` 时 trace 快照可读，UI 不会看到半成品。

### 4.2 规则

- 暂停只发生在安全边界：`after_scheduler` / `after_layer:core|platform` / `after_tick`；**绝不在 `ctx.emit` 内**；
- 层边界暂停后，同一层可连续求值多个阶段（A5 S1→S2）；
- `stop()` 必须能唤醒 `pause_at`，不能卡在 Condition；
- 当前没有单控制者；多个浏览器可并发 step，属于已知限制。

### 4.3 为什么不在 `ctx.emit` 内暂停

- 检测时延用 `monotonic_ns` 计算（[reference.py](../../isacsim/detect/reference.py)）；在 emit 里等人点“下一步”，时延会被讲解时间污染；
- 仿真线程被阻塞时，`stop`/reset 可能卡住；
- 一个 tick 内可能有几百条 emit，逐条暂停没有演示价值。

### 4.4 暂停点：同 tick 内的步骤怎么分

A1 在 `t0` 这个 tick 里会连续发生：`attack.start` → `sensing.objects` 注入 → `control.command`。如果只在 tick 末尾暂停，S1/S2 会挤在同一帧。

当前实现分三档：

| 暂停点 | 位置 | 当前用途 |
|---|---|---|
| `after_scheduler` | `scheduler.tick()` 后、`sensing.tick()` 前 | A5 S0（A1 无 S0） |
| `after_layer:core` | `core.tick()` 后、auth/platform 前 | A5 S1/S2 |
| `after_layer:platform` | `platform.tick()` 后、control 前 | A5 S3 |
| `after_tick` | 整个 tick 结束后 | A1 S1–S5；A5 S4/S5/END |

> `after_scheduler` 发生在 `sumo.step()` 之后、各层之前：车辆位置已经更新，但感知/通信/控制尚未执行；`t` 仍是本 tick 的起始值。

实现代价：

- `step_once()` 在 core/platform 后显式调用 `trace.after_layer`；
- 暂停期间 `t` 不前进，但 `ctx` 保持有效；
- UI 用 `last_layer`/`pause_reason` 标明“同一 tick 的阶段”；
- 不在 `ctx.emit` 内、不在 SUMO 调用中暂停。

A1 当前仍只在 `after_tick` 暂停；`after_sensing` 拆分 A1 S1/S2 仍是规划。

## 5. `StepFrame` 的生成

一次 step 的生命周期：

```text
1. 记录起点 cursor（seq/tick/t）
2. 设置 target_cursor / breakpoint
3. 仿真线程推进到边界，TraceService 持续写 store
4. 命中 checkpoint（安全边界）
5. 生成 StepFrame：
   - 区间 [from, to]
   - before/after：目标全量快照
   - events：区间内事件（最多 80）
   - alerts
6. 暂停，返回 StepFrame
```

`before` 取“起点前最后一个稳定帧”，`after` 取“命中边界后的帧”。默认用 tick 末尾，避免把半成品当结果；`after_scheduler`/`after_layer` 是显式的例外。

## 6. 检查点：A1 与 A5

### 6.1 A1（已实现，无 S0）

| 步骤 | 检查点 | 触发 | 暂停点 |
|---|---|---|---|
| S1 | 目标列表被篡改 | `ghost.added` | `after_tick` |
| S2 | ADAS 误判 | 首条 `control.command` | `after_tick` |
| S3 | 通信负载上升 | `pc5.rise` | `after_tick` |
| S4 | 物理后果 | `vehicle.speed_drop` | `after_tick` |
| S5 | 检测证据 | 首条 `alert` | `after_tick`（等 S4 0.5 s） |
| END | 攻击结束 | `attack.end` | `after_tick` |

### 6.2 A5（已实现）

| 步骤 | 检查点 | 触发 | 暂停点 |
|---|---|---|---|
| S0 | 信令风暴开始 | `attack.start` | `after_scheduler` |
| S1 | AMF 过载/拒绝 | `core.nas` + reject/overload | `after_layer:core` |
| S2 | PDU 会话失败 | `core.session` reject | `after_layer:core` |
| S3 | 平台 Ingest/云控 | `app.ingest`/`app.control` | `after_layer:platform` |
| S4 | 远控/物理后果 | `control.command`/速度下降 | `after_tick` |
| S5 | 检测告警 | `alert` | `after_tick` |
| END | 攻击结束 | `attack.end` | `after_tick` |

注意：

- A1 第一步是 S1（注入后的状态）；没有 S0。
- A5 S0 只有在 `step(mode="checkpoint")` 已进入 checkpoint 时才停；如果攻击已连续运行再冻结，S0 可能已错过。
- A5 S1/S2 都在 core 后；实现用 `after_layer` 循环，每次 step 放行一个 StepFrame。
- S3/S4/S5 有顺序等待，避免平台/控制事件抢在会话失败之前。
- 检查点不一定命中；未命中时由 `MAX`（2 s）兜底或攻击结束。
- S5 可能没有告警；当前不会生成“未触发”占位 StepFrame。

## 7. 层序与“丢失的状态”

A1 的 ADAS 制动在 `control.tick()` 产生，而 `v2x.tick()` 在它之前；`brake_events`/`emergency_until` 写在每个 tick 重建的 `ctx.extras` 里，下一个 tick 就丢。结果：

- 物理制动会发生；
- 但不会产生 ADAS DENM/CAM 20 Hz。

单步/检查点设计不能假设“制动 → DENM”一定发生。检查点应分别观察：

- `control.command`（制动指令）；
- `veh:<victim>.state` 的 `speed`（物理后果）；
- `v2x.denm`（可能是攻击伪造，也可能是其他路径）。

详细数据差异见 [A1 攻击实现解析 §9–§10](../09-A1攻击实现解析.md)。

## 8. 多攻击与 focus（未实现）

- 当前没有 `focus`：`TraceService` 以最近启动的攻击 profile 为准；
- 多攻击并存时按 `attack_id` 过滤阶段事件，避免 A1 的 `attack.start` 被 A5 的 S0 误用；
- 规划中：`focus=ATK001` 只按该攻击的检查点暂停，其他攻击仍记录；
- 当前没有单控制者；多浏览器并发 step 是已知限制。

## 9. 边界情况

| 情况 | 当前行为 |
|---|---|
| 攻击在 `t0` 之前暂停 | 页面显示“等待”；没有“跳到下一次攻击” |
| 检查点永远不命中 | `after_tick` 2 s 后 `MAX`；层边界不产生 MAX |
| 攻击被取消 | `attack.end` 可能不产生；后续检查点失效 |
| 仿真结束 | 页面显示 stopped；没有 `session.end` 事件 |
| 无攻击 | 只可手动/tick 单步；没有 checkpoint |
| 暂停中断线 | 重连重新拉 full snapshot；不保证 StepFrame 增量 |
| 多客户端同时 step | 当前没有 409/owner，存在并发风险 |
| 单步时 SUMO 报错 | 当前未单独封装错误 StepFrame |

## 10. 确定性验收

同 seed、同场景、同攻击参数：

- 连续运行 vs 单步运行，所有记录的 `ts_ns/source/entity/payload` 与 truth 事件应一致；
- `t_wall_ns`、检测时延、trace seq 可以不同；
- 不因暂停改变 RNG 消耗顺序；
- 不因 trace 开关改变 `sensing.last_objects`/检测器输入。

这是 trace 层最重要的回归测试。

## 11. 当前用户操作流程

```text
打开 /trace
  → 主控制台启动仿真
  → 冻结
  → 注入 A1 或 A5
  → 点“下一步”逐检查点
  → 可“继续”恢复；可“冻结”随时看
  → stop 后当前快照只在本进程内（导出/回放未实现）
```

当前快捷键：

- `Space`：下一步（检查点）；
- `F`：冻结/继续。

`T`/`B`/`Esc`/`/` 等快捷键仍是规划。
