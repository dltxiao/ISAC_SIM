# 05 单步断点与时间模型

## 1. 三个时间概念

| 概念 | 定义 | 例子 |
|---|---|---|
| tick | 仿真步，默认 50 ms | `t=3.10, tick=62` |
| checkpoint | 攻击链上的语义点，不等于 tick | “首次出现幽灵”“首条 TTC 制动” |
| step | 从当前暂停点推进到下一个断点 | `S1 → S2` |

**演示用的是 checkpoint，不是 1200 个 tick。** tick 单步只作为调试高级选项。

## 2. 运行模式

```text
                 ┌─────────────┐
                 │    idle     │
                 └──────┬──────┘
                        │ start
                 ┌──────▼──────┐
        ┌───────►│    live     │◄───────┐
        │        └──────┬──────┘        │
        │               │ pause         │ resume
        │        ┌──────▼──────┐        │
        │        │   paused    │────────┘
        │        └──────┬──────┘
        │               │ step(tick|checkpoint)
        │        ┌──────▼──────┐
        └────────│  stepping   │
                 └──────┬──────┘
                        │ hit breakpoint
                 ┌──────▼──────┐
                 │   paused    │
                 └─────────────┘
```

另外有 `replay` 模式，不启动 SUMO，状态机是 `paused/playing/scrubbing`，与 live 分开。

## 3. 断点类型

### 3.1 时间

```json
{"type": "time", "at": 3.0, "relative_to": "t0"}
```

用于“攻击开始/结束”“t0+1 s 注入制动”等确定时间点。

### 3.2 阶段

```json
{"type": "stage", "stage_id": "S2", "edge": "enter"}
```

需要 profile/攻击实例提供阶段事件。当前 A1 的 `truth.stages` 是计划，不是运行时事件；短期可用时间/记录触发，长期再让剧本显式发 stage。

### 3.3 首次记录

```json
{"type": "first_record", "stream": "sensing.objects",
 "where": {"sensor_id": "$rsu"}, "predicate": "ghost_added"}
```

用于“首次注入”“首条 DENM”“首条 CAM 位置跳变”。

### 3.4 首次变化

```json
{"type": "first_delta", "target_id": "sensor:$rsu.objects",
 "field": "ghost_count", "op": ">", "value": 0}
```

比解析原始记录更通用；适合 A2/A3/A4 的字段级变化。

### 3.5 告警

```json
{"type": "alert", "rule": "ghost_object", "entity": "rsu:$rsu"}
```

用于“检测器第一次看到”。

### 3.6 效果

```json
{"type": "effect", "target_id": "veh:$victim.state",
 "field": "speed", "op": "drop", "value": 0.5, "window_s": 0.5}
```

用于“车辆真的减速”，避免只看指令不看结果。

### 3.7 组合

```json
{"type": "all", "of": [
  {"type": "stage", "stage_id": "S1"},
  {"type": "first_delta", "target_id": "sensor:$rsu.objects"}
]}
```

只支持 `all/any`，不做任意表达式求值；避免安全/可复现性问题。

## 4. 暂停协议

### 4.1 当前实现的问题

- `pause()` 只置 `_paused`，run loop 下一次循环才看到；
- `state` 立即变 `paused`，但线程可能还在 tick 里；
- 紧接着 `resume/step` 会产生竞态。

### 4.2 设计

用 `threading.Condition` 做“停稳确认”：

```text
API 线程                         仿真线程
────────                          ────────
pause()                           while not stop:
  request = PAUSE                   if mode == PAUSED:
  notify()                            ack_paused = True
  wait(ack, timeout=2s)              cond.wait()
  return paused                   step_once()
                                    trace.after_tick()
                                    if breakpoint.hit():
                                        mode = PAUSED
                                        ack_paused = True
```

规则：

- 暂停只发生在**安全边界**：默认是 tick 末尾；S0 可在 `scheduler.tick()` 之后、感知之前；可选层边界；**绝不在 `ctx.emit` 内**；
- `step()` 同步等待“本次 step 完成 + 已再次暂停”，再返回 `StepFrame`；
- `step()` 超时返回 504，仿真状态保持可查询；
- `stop()` 必须 `notify_all()`，不能卡在 `cond.wait()`；
- 多个浏览器共享同一会话：控制权用简单的 `control_owner`/last-writer 或“只允许一个控制客户端”。

### 4.3 为什么不在 `ctx.emit` 内暂停

- 检测时延用 `monotonic_ns` 计算（[reference.py](../../isacsim/detect/reference.py:56)）；在 emit 里等人点“下一步”，时延会被讲解时间污染；
- 仿真线程被阻塞时，`stop`/reset 可能卡住；
- 一个 tick 内可能有几百条 emit，逐条暂停没有演示价值。

### 4.4 暂停点：同 tick 内的步骤怎么分

A1 在 `t0` 这个 tick 里会连续发生：`attack.start` → `sensing.objects` 注入 → `control.command`。如果只在 tick 末尾暂停，S0/S1/S2 会挤在同一帧，观众看不到“先注入、后制动”的顺序。

设计上分三档：

| 暂停点 | 位置 | 默认 | 用途 |
|---|---|---|---|
| `after_scheduler` | `scheduler.tick()` 后、`sensing.tick()` 前 | 是（S0） | 展示选目标/参数，注入尚未发生 |
| `after_layer(name)` | 任意两个层之间，例如 `sensing` 后 | 否（可选） | 把 S1（目标列表）与 S2（控制指令）拆开 |
| `after_tick` | 整个 tick 结束后 | 是（S1–S5） | 默认；状态稳定、无锁、无半成品 |

> `after_scheduler` 发生在 `sumo.step()` 之后、各层之前：车辆位置已经更新，但感知/通信/控制尚未执行；`t` 仍是本 tick 的起始值。UI 需要标明“世界已推进、层未执行”。

`after_layer` 的代价：

- `step_once()` 需要拆成“阶段”或在层间插入 `TraceService.checkpoint()`；
- 暂停期间 `t` 不前进，但 `ctx` 保持有效；
- UI 要显示“同一 tick 的阶段”，避免误解时间；
- 不是所有层都适合暂停（不能在 `ctx.emit` 内、不能在 SUMO 调用中）。

**v1 建议**：只用 `after_scheduler` + `after_tick`；如果 S1/S2 同 tick，StepFrame 合并为“注入 + 首次制动”，用子事件分组展示。**v1.1** 再为 A1 加 `after_sensing`，把两步拆开。

## 5. `StepFrame` 的生成

一次 step 的生命周期：

```text
1. 记录起点 cursor（seq/tick/t）
2. 设置 target_cursor / breakpoint
3. 仿真线程推进 tick，probes 持续写 store
4. 命中 breakpoint（安全边界：scheduler 后 / 层间 / tick 末尾）
5. 生成 StepFrame：
   - 区间 [from, to]
   - before/after：受影响的 targets
   - events：区间内关键事件
   - effects：速度/CBR 等摘要
6. 暂停，返回 StepFrame
```

`before` 取“起点前最后一个稳定帧”，`after` 取“命中边界后的帧”。默认用 tick 末尾，避免把半成品当结果；`after_scheduler`/`after_layer` 是显式的例外。

## 6. 检查点设计：A1 示例

| 步骤 | 检查点 | 触发 | 展示 |
|---|---|---|---|
| S0 | 选目标与参数 | `attack.start` | RSU-01、eastbound.2、3 个 ghost、450 msg/s |
| S1 | 目标列表被篡改 | 首帧 `sensing.objects` 含 `ghost:*` | 3→6，新增 9000/9001/9002 |
| S2 | ADAS 误判 | 首条 `control.command(reason=ttc)` | TTC 1.481、decel 3.0 |
| S3 | 通信负载上升 | `net:pc5.offered` 上升 >100 或 CBR 上升 >0.1 | offered 120→570、CBR 0.092→0.437 |
| S4 | 物理后果 | 受害车速度下降 >0.5 m/s | 14.86→12.32 |
| S5 | 检测证据 | 首条 `ghost_object`/`cbr_spike` | rule/entity/detail/latency |

注意：

- S0 建议用 `after_scheduler` 暂停，否则会和 S1 挤在同一 tick；
- S1/S2 在 seed=14 的 t0 同一 tick：v1 可合并为一个 StepFrame，用子事件展示“目标列表 + 首条制动”；v1.1 可用 `after_sensing` 拆开；
- S2 不一定发生（受害车未装备/未被目标 RSU 覆盖）；检查点要允许“未命中”；
- S3 的阈值要可配，不能写死 0.437；
- S5 可能没有告警；StepFrame 要明确“未触发”及原因，而不是空白；
- 如果攻击结束仍未命中，最后一步是 `attack.end` + 汇总。

## 7. 层序与“丢失的状态”

A1 的 ADAS 制动在 `control.tick()` 产生，而 `v2x.tick()` 在它之前；`brake_events`/`emergency_until` 写在每个 tick 重建的 `ctx.extras` 里，下一个 tick 就丢。结果：

- 物理制动会发生；
- 但不会产生 ADAS DENM/CAM 20 Hz。

单步/检查点设计不能假设“制动 → DENM”一定发生。检查点应分别观察：

- `control.command`（制动指令）；
- `veh:<victim>.state` 的 `speed`（物理后果）；
- `v2x.denm`（可能是攻击伪造，也可能是其他路径）。

详细数据差异见 [A1 攻击实现解析 §9–§10](../09-A1攻击实现解析.md)。

## 8. 多攻击与 focus

- 默认 `focus=null`：所有攻击的检查点都可能触发，StepFrame 包含多个 attack 的事件；
- 演示时 `focus=ATK001`：只按该攻击的检查点暂停，其他攻击仍记录但不打断；
- 全局目标（PC5、fleet）始终更新；
- UI 显示“其他攻击也在运行”提示，避免观众误解；
- 如果两个攻击同 tick 命中，StepFrame 合并，按 `attack_id` 分组。

## 9. 边界情况

| 情况 | 行为 |
|---|---|
| 攻击在 `t0` 之前暂停 | 页面显示“等待 A1 开始”；可“跳到下一次攻击” |
| 检查点永远不命中 | 达到 `max_step_s`（默认 2 s 仿真时间）后暂停，reason=`max_step` |
| 攻击被取消 | 发 `attack.cancel`；后续检查点失效；已注入数据是否残留由实现决定，trace 如实显示 |
| 仿真结束 | 发 `session.end`；最后生成 summary；页面进入只读 |
| 无攻击 | 只按“手动/定时”单步；没有 checkpoint |
| 暂停中断线 | 重连后从当前 cursor 恢复；StepFrame 不丢 |
| 多客户端同时 step | 409 或排队；只允许一个控制者 |
| 单步时 SUMO 报错 | 返回 500/错误 StepFrame；保留现场 |

## 10. 确定性验收

同 seed、同场景、同攻击参数：

- 连续运行 vs 单步运行，所有记录的 `ts_ns/source/entity/payload` 与 truth 事件应一致；
- `t_wall_ns`、检测时延、trace seq 可以不同；
- 不因暂停改变 RNG 消耗顺序；
- 不因 trace 开关改变 `sensing.last_objects`/检测器输入。

这是 trace 层最重要的回归测试。

## 11. 用户操作流程

```text
打开 /trace
  → 选择会话/run
  → 选择 focus（可选）
  → 点“开始追踪”/“跟随”
  → 自动停在 S0
  → 每次“下一步”看一张 StepFrame
  → 可“连续”恢复；可“冻结”随时看
  → 结束后“导出”
```

快捷键建议：

- `Space`：下一步（检查点）
- `T`：下一步（tick）
- `F`：冻结/继续
- `B`：设为基线
- `Esc`：取消选择
- `/`：搜索 target/字段
