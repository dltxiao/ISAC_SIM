# 通信层扩展评估：5G-A 核心网与车联网业务平台

> 评估对象：ISAC-SIM v0.2.0（HEAD `d045fe1`）  
> 评估日期：2026-10-27  
> 评估问题：当前模拟场景的感知与通信最多只到 gNB，是否有必要把通信层拓展到 5G-A 核心网（网络层）和车联网业务平台（应用层）？  
> 结论口径：分“只保指标”和“保完整任务书”两个口径，答案不同。

> **实施进展（2026-10-27）**：M0 已实施——A4 truth 中未实现的 `uu` 阶段已移除；Uu 已改为 gNB 覆盖/FOV 驱动；记录 schema 升为 `isacsim.record/2`；图增加 `veh→gNB` 与核心网边。M1 已实施 AMF/SMF/UPF/UDM/AUSF 最小闭环；M2 已实施 NEF + PlatformLayer（IAM/订阅/Ingest/云控/审计）；M3 已实施 A5/A7/A9 与 `defense.action`。本文 §1 的相关描述保留为“评估时基线”，并标注 M0 变更。

**阅读指引：**

- 只想做决策：看 §0、§7；
- 想看“为什么现在不够”：看 §1–§3；
- 想看“语义级怎么模拟、外部系统能不能接”：看 §4–§5；
- 想看方案2 的资源、依赖、复杂度：看 §6；
- 想查代码位置和术语：看 §8。

## 0 结论摘要

| 口径 | 结论 | 关键理由 |
|---|---|---|
| 只对任务②三项硬指标和四类官方攻击负责 | **不拓展** | A1–A4 的攻击面在 RSU/OBU/PC5/控制，核心网与平台不在因果链上；加层只增加正常波动、关联时延和维护成本 |
| 对任务书完整表述负责（端—链—平台、设备—网络—任务、跨物理层/跨网络域、图建模、隔离—阻断—恢复） | **需要拓展，但只做语义级两层** | 评估时“网络层”只占记录量 0.15%，A4 truth 还声明了一个不存在的 `uu:ghost_attach`（M0 已移除）；防御动作也没有网络/平台落点 |
| 外部系统抓 pcap 做 DPI/协议解析 | **语义级不够** | 语义事件没有 wire format；现有 CAM pcap 是 JSON-over-UDP；NAS 加密、N2/N4 常被 IPsec、NEF 常走 TLS，裸 pcap 的可见性本身就有限 |
| 外部系统消费结构化事件/特征/NetFlow | **语义级够，而且更合适** | 有实体、状态、因果、真值和 `trace_id`；可复现、可批量、可调幅度 |
| 方案2（Open5GS + UERANSIM + 真实平台） | **只适合实验室点验，不适合批量主循环** | 当前主机可做 1 gNB + 10–60 UE；需 root/系统层部署；代码量约方案1的 2–3 倍，集成运维约 4–6 倍 |

**推荐路线：**

1. **不替换**现有 SUMO + 语义层环境；保留其确定性、单机、事件级真值。
2. **P0**：修 truth 一致性、让 gNB 成为真正的 RAN 节点、加 `trace_id`、把评估从事件级升级到链级。
3. **P1**：加语义级 `CoreLayer` + `PlatformLayer`；改造 A1/A4；新增 A5/A7/A9。
4. **P2**：补 A6/A8/A10、`defense.action`、隔离/阻断/恢复。
5. **P3（可选）**：用 Open5GS + UERANSIM 做协议级点验，只导出样本，不进批量主循环。

## 1 现状基线

### 1.1 通信层目前只到“小区标签”

| 事实 | 证据 | 含义 |
|---|---|---|
| GNB-01 是第 4 个传感器 | `isacsim/config.py:134`、`isacsim/layers/sensing.py:58` | 20 Hz 雷达，只承担“感”，没有“通”的协议栈 |
| Uu 曾是定时器标签 | `isacsim/layers/uu.py:17` | 评估时默认 `CELL-1`，12–35 s 在 `CELL-1/2` 间翻转；M0 已改为 gNB 覆盖/FOV 驱动 |
| 图里曾没有无线/核心/平台边 | `isacsim/layers/edge.py:26` | 评估时只有 RSU 覆盖边 + `veh→net:uu`；M0 已加 `veh→gNB` 与 `gNB→AMF→SMF→UPF→DN` |
| 检测器不读 Uu/auth | `isacsim/detect/reference.py:64` | `on_record` 只处理 sensing/v2x/link/control，网络层和认证层证据没有进入检测 |
| A4 的 truth 曾声明 `uu:ghost_attach` | `isacsim/truth/model.py:26`、`isacsim/attacks/campaigns.py:310` | 评估时 `domains=[auth,v2x,uu]`；M0 已改为 `[auth,v2x]`，并从 causal_chain 移除未实现的 `uu` 阶段 |
| 评估只到事件级 | `isacsim/eval/metrics.py` | `nodes`/`domains`/`stages` 不参与评分，只按时间重叠匹配 |
| 防御只有刹车 | `isacsim/layers/control.py:125` | 没有 AMF 拒绝、SMF 释放、UPF 阻断、NEF 吊销、平台吊销 |

### 1.2 数据证据

本机 60 s / 60 车场景实测：

| 指标 | 数值 |
|---|---:|
| 总记录 | 212,464 条 |
| 总大小 | 112.9 MB（JSONL 未压缩） |
| `uu.*` | 310 条，占 **0.15%** |
| `auth.*` | 3,273 条，占 **1.54%** |
| 仿真耗时 | 17.7 s（约 3.4× 实时） |
| 1000×15 s 批处理 | 207 s（18 进程，不落流） |

也就是说，当前所谓“网络层”在数据里占不到 0.2%。这不是“通信层到 gNB”，而是“gNB 只做了感知，通信只有一个小区标签”。

### 1.3 五个结构性缺口

1. **网络层是标签，不是数据**：`uu.*` 极少，A4 的 `uu:ghost_attach` 更是只写在 truth 里。
2. **gNB 只感不通**：没有 RRC/N2/N3、没有 QoS、没有 PDU 会话、没有切换信令。
3. **图缺层**：没有 `veh→gNB`、`gNB→AMF`、`AMF→SMF`、`SMF→UPF`、`UPF→DN`、`DN→platform` 的边。
4. **检测与评估缺链**：检测器不读 Uu/auth；评估不校验 `nodes/domains/stages`，当前 100% 是事件级识别率，不是链级重建率。
5. **防御缺落点**：只有 AEB 刹车，没有“隔离—阻断—恢复”的网络/平台动作。

## 2 维度一：最低限度是否有必要拓展

### 2.1 只保三项指标：不必要

四类官方攻击的因果链都在终端/感知/PC5/控制，核心网与平台不在链上：

| 类型 | 攻击面 | 现有证据链 | 需要核心网/平台？ |
|---|---|---|---|
| A1 感知篡改→拥塞 | RSU 目标列表 + DENM + PC5 负载 | 目标列表→ADAS→制动→CBR | 否（除非 V2X 走 Uu） |
| A2 物理欺骗+控制误导 | RSU 目标列表 + 控制指令 + 链路干扰 | 假停止牌→制动→PER | 否 |
| A3 跨层隐蔽 | 雷达回波 + 控制 | 回波/点迹残差→小制动 | 否 |
| A4 双因素仿冒 | 证书/指纹 + CAM | 位置跳变 + CAM/GNSS 不一致 | 否（核心网可增强，但不是必需） |

共同原因：**攻击者已经在 RSU/OBU/PC5 的信任边界内**，核心网和平台不在因果链上。加层不会提高这四类的识别率，反而会：

- 引入注册风暴、切换乒乓、切片重配等新正常波动，抬高误检率；
- 让跨层关联需要凑窗，100 ms 时延口径变得更难守；
- 增加 root、网络、进程、端口、状态清理等运维面。

**如果本期只交这三项指标，建议冻结 v0.2 基线，不拓展。**

### 2.2 保完整任务书：必要，但只做轻量

任务②的原文不是只有四项指标，而是：

- “设备—网络—任务”多层级系统状态；
- “跨物理层、跨网络域”；
- 图建模与时空智能分析；
- “隔离—阻断—恢复”的分层协同防御。

当前环境最多是“设备—链路—任务”：网络和平台是空的，图只有一跳覆盖边，防御只有刹车。**“跨层”有了，“跨域”没有。**

还有两个现实约束：

1. **任务③现网验证**：真实环境有 gNB、核心网元、终端。当前 NIDD 适配器只导出 D0–D3 + CAM（`isacsim/io/adapters/nidd.py:52`），仍是感知/控制视角，没有核心网/平台数据。算法在仿真里训完，到现网会缺特征、缺接口。
2. **评审风险**：课题叫“5G-A 通信感知一体”，模拟环境里却没有 5G 核心网；A4 的 truth 已经声明了一个不存在的 Uu 阶段。与其答辩时解释，不如补一个轻量层。

### 2.3 三个方案对比

| 方案 | 做什么 | 对三项 KPI | 项目完整性 | 单机成本 | 建议 |
|---|---|---|---|---|---|
| 0 不拓展 | 现状 | 已满足 | 缺网络/平台 | 0 | 只保 KPI 时 |
| 1 语义级 | 2 层、8–10 类流、5–6 个新剧本 | 不降，略增时延 | 基本补齐 | +15–25% 记录 | **推荐** |
| 2 全协议 | Open5GS + UERANSIM + 真实平台 | 无增益 | 高 | 高，需 root/TUN，难并行 | 仅点验 |

方案2 不建议进本期主循环：UERANSIM 主要跑 Uu，不覆盖 PC5；无 root/TUN 受限；18 进程批处理也跑不动。它不会让 A1–A4 更可检，只会增加维护面。

### 2.4 推荐的最小扩展范围

不做“全栈 5GC”，做“逻辑核心网 + 逻辑平台”，进程内事件驱动，1–10 Hz，保持单机、确定性、可批处理。

| 层 | 最小实体 | 新增流 | 关键字段 |
|---|---|---|---|
| 核心网 | AMF、SMF、UPF、NEF、UDM/AUSF | `core.nas`、`core.session`、`core.qos`、`core.handover`、`core.upf`、`core.nef` | 5QI、S-NSSAI、cause、result、latency_ms |
| 平台 | API 网关/IAM、订阅、调度、审计 | `app.ingest`、`app.subscription`、`app.control`、`app.audit` | token、tenant、provenance、signature、ttl |
| 图 | `veh→gNB→AMF→SMF→UPF→DN→platform→veh` | `graph.snapshot` | latency、qos、trust |
| 防御 | AMF 拒绝/去注册、SMF 释放、UPF 阻断、NEF 吊销、平台吊销 | `defense.action` | action、result、latency、collateral |

**边界：**

- 不做 per-packet、真实 NAS/NGAP 编码、完整 5GC；
- 不做真实 V2X 平台的全量功能，只做 API/订阅/调度/审计；
- 不把语义层替换成真实 5GC；两者是 sidecar 关系；
- 不让攻击直接改 SUMO 世界状态，仍遵守“只改发射器输出”。

### 2.5 容量与成本

| 项 | 估算 |
|---|---|
| 记录量 | +15–25% |
| 单场景耗时 | +10–20%；60 s 从 17.7 s 到约 21 s |
| 单会话内存 | +50–100 MB |
| 1000×15 s 批处理 | 从 207 s 到约 250 s |
| 18 进程内存 | 仍 <5 GB |
| 代码量 | 约 +1,500 LOC |
| 工期 | 4–6 人周（2 人并行约 3 周） |

### 2.6 三个工程注意点

1. **Schema 要升版**：`schemas/record.v1.json` 的 `stream` 正则只允许 `sensing|v2x|uu|auth|control|task|link|graph`，`entity` 正则不允许 `amf/upf/platform`；`schemas/truth.v1.json` 的 `campaign` 枚举只有 A1–A4 + 8 原语。建议新增 `isacsim.record/2`，保留 v1 兼容读取。
2. **图快照 600 条边上限**：`isacsim/layers/edge.py` 的 `edges[:600]` 会在加层后截掉核心网/平台边，需改成分层图或 top-k 采样。
3. **`preflight` 公式要加项**：当前只按车/传感器估算，加 core/app 后要增加进程、消息速率、内存项，否则容量护栏失真。

## 3 维度二：拓展后可以同步做哪些跨层攻击

### 3.1 设计原则

1. **每条新攻击至少 3 层**，且有因果先后，不能只是“核心网单独发洪泛”。
2. **每个攻击至少有一个防御动作落在新增层**，否则加层只为了检测，防御仍是刹车。
3. **truth 的 `domains` 必须与实际写入的流一致**，加静态测试。
4. **定义可检出包络**，包络外单列，不污染识别率分母。
5. **正常集要加新层的难负样本**，否则 1% 误检率会被新层吃掉。

### 3.2 新增剧本

建议顺序：**A5/A7/A9 → A6/A8 → A10**。

| 编号 | 攻击 | 注入点 | 因果链（简） | 关键证据 | 域 |
|---|---|---|---|---|---|
| A5 | 信令风暴→远控失控 | 伪 UE/被控 OBU 发 NAS 注册/服务请求 | `core.nas` 洪泛→AMF 过载→PDU 建立失败→远控指令老化→任务偏差 | 注册速率、AMF 队列、会话失败、指令年龄 | uu/core/app/task/control |
| A6 | 切片/QoS 抢占 | NEF/OSS 越权改 5QI/GFBR，或耗尽切片 | `core.qos` 5QI 79/80→9→UPF/空口排队→CPM 丢失→AEB 晚 | QoS 变更无工单、切片利用率、Uu 时延、CPM 丢失 | core/app/v2x/control |
| A7 | UPF/N6 劫持 | 路由/DNS 劫持或 UPF 被控 | `core.upf` 改路由→`app.ingest` 来源不符→伪造 CPM→车辆制动 | 流表/来源/provenance、CPM 与 RSU 不一致 | core/app/v2x/control |
| A8 | NEF/订阅篡改 | 盗用 NEF token/租户 token | `core.nef` 退订 DENM/SPaT→`app.subscription` 差异→缺失告警/错误相位→路口冲突 | 订阅变更无工单、事件缺失、SPaT 与 RSU 不符 | core/app/v2x/task |
| A9 | 平台越权/云控注入 | 盗用服务账号/token | `app.auth` 异常→`app.control` 批量制动→`control.command` TTC=99→拥堵 | token scope、指令突发、无危险依据 | app/control/task/v2x |
| A10 | 跨层隐蔽组合 | A3 雷达渐偏 + 轻量 A5 + 平台审计抑制 | 雷达残差+核心网抖动+审计缺失，单层均不超门限 | 多源残差、日志缺失、时序相关 | radar/perception/core/app/control |

**防御动作：**

- A5：AMF 限流/拒绝、SMF 释放、平台降级 PC5；
- A6：PCF/SMF 恢复 QoS、切片隔离、RAN 预留 PRB；
- A7：UPF 回切、平台隔离来源、车辆忽略；
- A8：吊销 token、恢复订阅、回退本地 RSU；
- A9：吊销 token、限流、车辆要求本地危险确认；
- A10：链级隔离、恢复审计、降级。

**可选的高价值 5G-A 特色攻击：**

- **A11 切换风暴/伪 gNB**：N2 handover race→CPM 中断→远控掉线；
- **A12 时间同步欺骗**：核心网/边缘授时偏移→传感器融合/TTC 错判。

### 3.3 改造现有 A1–A4

不用推翻，升级成“端—网—云”版本：

- **A1**：增加 Uu 路径，RSU→gNB→UPF→平台→其他车；PC5 和 Uu 同时加压，平台扇出放大。
- **A2**：增加平台调度，假停止牌 + 平台签发的云控制动；链路干扰同时打 Uu 和 PC5。
- **A3**：增加边缘/时间/审计掩盖，雷达渐偏 + 小制动 + 平台日志抑制。
- **A4**：增加 AMF/UDM/AUSF 认证和平台 token，让 `uu:ghost_attach` 变成真实事件；检测用“标识+指纹+网络认证上下文”，而不是只看 CAM 跳变。

这样原有四类从“边缘跨层”升级为“端—网—云跨域”，且不破坏现有回归。

### 3.4 新增原语

`registration_flood`、`pdu_session_drop`、`qos_downgrade`、`slice_exhaust`、`upf_redirect`、`nef_subscription_tamper`、`platform_token_replay`、`cloud_control_inject`、`audit_suppress`、`time_sync_spoof`、`handover_storm`。

都遵守现有 `HookBus` 约束：只改发射器输出，不碰 SUMO 世界状态；涉及防御的通过 actuator 回写。

### 3.5 检测与评估要同步升级

新增跨源一致性比较：

| 比较 | 异常含义 |
|---|---|
| `core.nas` ↔ `uu.attach` | 注册量远大于合法 UE 数 |
| `core.session` ↔ `uu.session` | 建立失败/释放异常 |
| `core.qos` ↔ `link.metrics` | 5QI/GFBR 变化与 Uu 时延/PER 不一致 |
| `core.upf` ↔ `app.ingest` | 流表路由与消息来源不一致 |
| `core.nef` ↔ `app.subscription` | 订阅变更与变更管理不一致 |
| `app.control` ↔ `control.command` ↔ `sensing.objects` | 云控指令无危险依据 |
| `app.audit` ↔ 全流 | 审计缺失/被抑制，本身就是证据 |

**评估要从“事件级”升级到“事件级 + 链级”：**

- 事件级：现有 recall / false positive；
- 链级：节点/边 recall/precision、阶段顺序、根因 top-1、链完整度；
- 时延：首证据→告警；攻击发生→链确认；防御动作时延。

当前 0.08 ms 是**单条记录规则时延**，不是链级关联时延。加层后如果检测器要等 0.5–2 s 的多源窗口，`t_onset→t_decide` 会超 100 ms。建议保留两条口径：**快路径（单条/短窗，≤100 ms）** 和 **链确认（单列）**，验收时明确主口径。

**必须补的难负样本：**

- 大型活动散场：注册风暴；
- 小区边缘：切换乒乓；
- 切片重配/割接：QoS 变更；
- UPF 主备切换：路由变化；
- 平台 token 轮换/订阅变更：合法变更；
- 时间同步调整：授时漂移；
- 消息重传/重复：重复 CPM/DENM。

不加这些，新增层的误检率会直接把 1% 吃掉。

## 4 语义级如何模拟 5G-A 核心网

### 4.1 建模原则

把每个 NF 当成“状态机 + 队列 + 消息总线”，不实现协议栈：

```text
CoreNetwork
 ├─ AMF   注册/移动性/N1/N2/切换
 ├─ SMF   PDU 会话/QoS flow/UPF 选择
 ├─ UPF   TEID/流表/QoS 执行/N6 路由
 ├─ NEF   API 订阅/token/事件通知
 ├─ UDM   签约/SUPI/鉴权状态
 ├─ AUSF  5G-AKA 鉴权
 ├─ PCF   策略/QoS（可选）
 └─ NRF   NF 发现（可选）
```

### 4.2 每个 NF 的职责与状态

| NF | 语义状态 | 关键事件 | 可被攻击的字段 |
|---|---|---|---|
| **AMF** | UE 注册态、CM-IDLE/CONNECTED、认证态、N2 关联、切换上下文 | `registration_request/accept/reject`、`auth_request/response`、`security_mode`、`handover_required/request/ack` | 注册速率、队列深度、拒绝原因、切换次数 |
| **SMF** | PDU 会话表、QoS flow 表、IP 地址池、UPF 选择 | `pdu_session_establish/modify/release`、`qos_flow_create/modify/delete` | 5QI、GFBR、会话数、失败原因 |
| **UPF** | TEID/流表、QoS 执行、N6 路由、队列 | `flow_install/update/delete`、`forward/drop`、`route_change` | 路由、DN、QFI、吞吐、丢包/时延 |
| **NEF** | API 订阅表、token/scope、事件通知 | `api_subscribe/notify/revoke`、`api_error` | 订阅范围、token、回调地址、QPS |
| **UDM** | 用户签约、SUPI/SUCI、认证状态、切片签约 | `subscription_query`、`auth_data_request/response` | 签约数据、鉴权状态、允许的 S-NSSAI |
| **AUSF** | 5G-AKA 鉴权向量、鉴权结果 | `auth_request/response`、`auth_failure` | 鉴权结果、向量、失败原因 |

### 4.3 过程引擎

不要用真实 socket，用进程内 `CoreBus`：

```python
bus.send(src="ue:OBU-004", dst="amf:AMF-01",
         msg_type="registration_request",
         payload={"supi": "...", "gnb": "GNB-01", "snssai": "01-000001"},
         trace_id="tr-...")
```

每个过程写成一个小状态机，按 3GPP 过程顺序推进：

```text
注册：
UE → gNB → AMF(registration_request)
AMF → AUSF(auth_request) → UDM(auth_data) → AUSF(auth_response)
AMF → UE(auth_request / security_mode_command / registration_accept)

PDU 会话：
UE → AMF → SMF(pdu_session_establish)
SMF → UPF(N4 session_establish)
SMF → gNB(N2 resource_setup)
SMF → UE(pdu_session_establish_accept)

切换：
源 gNB → AMF(handover_required)
AMF → 目标 gNB(handover_request)
AMF → SMF(handover_commit)
SMF → UPF(N4 path_switch)
目标 gNB → AMF(handover_notify)

NEF：
AF → NEF(api_subscribe)
NEF → UDM/PCF(授权/策略查询)
NEF → AF(api_subscribe_response / notify)
```

每个步骤 emit 一条 `core.*` 记录，带 `trace_id`、`msg_type`、`result`、`cause`、`latency_ms`、`queue_depth`。

### 4.4 容量与排队模型

语义级不需要真实硬件性能，但要能表现“过载”：

```text
arrivals = 本步到达的消息数
service  = capacity_per_s * dt
queue    = max(0, queue + arrivals - service)
drop     = max(0, arrivals - service - queue_capacity)
latency  = base_latency + queue / service_rate
```

示例参数（可标定，不是现网值）：

| NF | 容量示例 | 队列 | 过载表现 |
|---|---|---|---|
| AMF | 5,000 注册/s | 1,000 | 注册拒绝、时延上升 |
| SMF | 2,000 会话/s | 500 | PDU 建立失败 |
| UPF | 10 Gbps | 10 ms | 排队/丢包、QoS 降级 |
| NEF | 1,000 API/s | 200 | 429/503、订阅失败 |
| UDM/AUSF | 3,000 鉴权/s | 500 | 鉴权超时/失败 |

建议用**归一化负载**（0–1）或相对容量，避免假装成现网精确值；关键是让 A5/A6 这类攻击能产生可观测的排队、拒绝、时延。

### 4.6 正常流程与攻击流程

正常流程：

```text
t=0.00  uu.attach          UE → gNB
t=0.01  core.nas           registration_request  UE → AMF
t=0.02  core.nas           auth_request          AMF → AUSF
t=0.03  core.nas           auth_response         AUSF → AMF
t=0.04  core.nas           registration_accept   AMF → UE
t=0.10  core.session       pdu_session_establish UE → AMF → SMF
t=0.12  core.qos           qos_flow_create       SMF → UPF/gNB (5QI 79)
t=0.15  core.upf           flow_install          UPF → DN
t=0.20  app.ingest         platform 收到 CPM
t=0.21  v2x.cpm            downlink 给车辆
```

攻击流程：

- **A5**：200 个 UE 以 1000/s 发 `registration_request` → AMF 队列 > 500 → 注册拒绝 → PDU 会话失败 → 远控指令年龄 > 200 ms → 任务偏差。
- **A6**：NEF/OSS 改 5QI 79→9 → `core.qos` 变更 → UPF 排队 → `link.metrics` Uu 时延上升 → CPM 丢失 → AEB 晚。
- **A7**：UPF 路由改到恶意 DN → `app.ingest` 来源不符 → 伪造 CPM → 车辆制动。
- **A8**：NEF 退订 DENM/SPaT → `app.subscription` 差异 → 缺失告警/错误相位。
- **A9**：平台 token 被盗 → `app.control` 批量制动 → `control.command` TTC=99。

### 4.7 不模拟的部分

- 不实现 NAS/NGAP/PFCP/GTP-U 的 ASN.1/二进制编码；
- 不实现 SCTP/GTP-U/TLS 协议栈；
- 不模拟 RF/PHY/RLC/MAC；
- 不保证 3GPP 协议一致性；
- 不模拟厂商实现差异和现网容量。

这些是“协议投影”或“真实 5GC”的职责，不是语义层的职责。

## 5 外部系统抓数据/流量能否满足

### 5.1 输入类型判断

| 外部系统输入 | 语义级是否够 | 说明 |
|---|---|---|
| JSONL/Parquet/Kafka 事件 | ✅ 够 | 最适合；有实体、状态、因果、真值、`trace_id` |
| NetFlow/IPFIX/sFlow | ✅/⚠️ 基本够 | 需要从语义事件生成五元组、bytes、packets、latency；不含 payload |
| pcap + 只看五元组/包长/到达间隔 | ⚠️ 要补投影 | 需要生成头部正确的包；不要求完整协议 |
| pcap + DPI/协议解析/状态机 | ❌ 不够 | 需要 NAS/NGAP/PFCP/GTP-U/HTTP2 的真实编码和状态一致性 |
| 真实网元日志/syslog | ⚠️ 可映射 | 语义事件可转成日志格式，但要按对方字段规范 |
| TLS 指纹/PHY/RLC/MAC 特征 | ❌ 不够 | 语义层不模拟这些层 |

### 5.2 语义级够用/不够用的边界

**够用：**

- 跨层攻击链的**逻辑、因果、特征**检测；
- 事件级/链级算法研发；
- 标签、复现、批量、消融实验；
- 流级/会话级特征（从语义事件推导）。

**不够用：**

- wire-level DPI、协议一致性；
- 加密流量内部字段；
- RF/PHY/RLC/MAC 特征；
- 厂商实现差异；
- 需要真实状态机的 IDS。

### 5.3 pcap/DPI 的三个缺口

1. **现有 CAM pcap 不是真 CAM**  
   `isacsim/io/pcapng.py:56` 是“Ethernet/IPv4/UDP 里装 JSON”，`isacsim/io/adapters/nidd.py:100` 用它导 CAM。自定义解析器/特征管线可以吃，但 Wireshark/tshark 的 CAM dissector 会解不出来，因为 ETSI CAM 是 ASN.1 UPER。

2. **真实 5GC 抓包也未必能看到 NAS**  
   N1/N2 的 NAS 在鉴权/安全模式之后是加密的；N2/N4 在现网常用 IPsec；NEF 常用 TLS。被动抓包只能看到部分消息类型，看不到完整 IE。如果外部系统要求“看到 NAS 里的注册原因、切片、QoS”，它需要密钥/解密能力，或者改用网元遥测/日志。

3. **DPI 是状态机，不是单包解析**  
   即使生成 pcap，也要保证 NGAP UE ID、PDU 会话、PFCP TEID、GTP-U、5QI/QFI 前后一致；请求/响应顺序、cause code、重传合理；时间戳单调。随机拼包能过 `tshark` 单包解析，但过不了有状态 IDS。

### 5.4 三层接口

```text
语义层（NF 状态机 + 队列 + 消息总线）
  ├─ Tier 1：JSONL / Parquet / Kafka 事件
  │     → 外部检测算法（推荐，标签/因果/复现最好）
  ├─ Tier 2：NetFlow / IPFIX / 自定义特征表
  │     → 外部流量分析/ML（不需要 payload）
  └─ Tier 3：协议投影 pcap
        → 外部 DPI（需要 NGAP/NAS/PFCP/GTP-U/HTTP2 编码）
```

**Tier 1（首选）**：有 `trace_id`，能把 RSU 目标、AMF 注册、SMF 会话、UPF 流、平台消息串成一条链；有真值 `t0/t1`、`domains`、`stages`、`causal_chain`；可复现、可调幅度、可批量。

**Tier 2（流记录）**：生成 `src/dst/port/proto/bytes/packets/duration/latency/retransmits`；可以从语义事件推导，不需要真包；对 A5/A6/A7 的拥塞、路由、QoS 攻击足够。

**Tier 3（协议投影）**：只在外部系统明确要求 pcap/DPI 时做。用 `pycrate`/`asn1tools` 编 NAS/NGAP，`scapy` 做 SCTP/GTP-U，`h2` 做 HTTP2；只做关键过程 + 关键 IE，不做全量协议栈；用 `tshark -r` 验证可解析，用状态机验证顺序；明确声明“合成流量，非现网一致性”。

**Tier 4（可选）**：Open5GS + UERANSIM 真实 5GC 点验。生成真实 NAS/NGAP/PFCP/GTP-U pcap，用来校准语义层和外部系统；但 UERANSIM 主要跑 Uu，不覆盖 PC5；需要 root/TUN，难并行，不适合批量。

### 5.5 外部系统联调建议

先问三个问题：

1. **输入格式**：pcap、NetFlow/IPFIX、JSON/Parquet/Kafka、syslog，还是 API？
2. **协议深度**：只看五元组/统计，还是要解析 NAS/NGAP/PFCP/GTP-U/HTTP2？要不要状态机重组？
3. **标签与时延**：要事件级真值、链级真值，还是只要异常分数？离线还是实时？

然后做一次 10 分钟联调：导出 1 个正常场景 + 1 个 A5/A7 场景，按对方格式给对方，确认它能读、能对齐时间、能输出告警，再决定是否投入协议投影。

## 6 方案2：全协议（Open5GS + UERANSIM）评估

### 6.1 方案2的范围

> 方案2 = Open5GS（5G SA 核心网）+ UERANSIM（gNB/UE）+ 现有/真实 V2X 平台 + pcap 采集。

它**不是完整 5G-A**：

- Open5GS 支持 5G SA、切片、QoS、UDM/AUSF；NEF 支持有限；不覆盖 NWDAF/RedCap/NTN/ISAC；
- UERANSIM 主要是 Uu，不覆盖 PC5；
- 5G-A 的 ISAC、RedCap、NTN、NWDAF 需要定制/商业核心网；
- V2X PC5 仍然走语义层。

**因此方案2 是 sidecar，不是替代。**

### 6.2 硬件资源

#### 当前基线

| 项 | 实测 |
|---|---|
| Windows | Windows 10 19045，WSL2 NAT |
| CPU | 24 逻辑核（Xeon E5-2673 v3） |
| 宿主内存 | 34.2 GB |
| WSL 内存 | 当前 15.5 GB |
| 磁盘 | 927 GB 可用 |
| 当前仿真 | 60 s/60 车 17.7 s，212k 条记录，单会话约 132 MB |
| 当前批处理 | 1000×15 s，18 进程，207 s |

5GC 的瓶颈不是 CPU，是 **WSL 内存**（15.5 GB）和 **UERANSIM 的进程数**。

#### 三档配置

| 档位 | 规模 | vCPU | RAM | 磁盘 | 当前主机 |
|---|---|---|---|---|---|
| **最小验证** | 1 gNB + 5–10 UE + 轻量平台 + SUMO | 4–6 | 8–10 GB | 30–50 GB | ✅ 15.5 GB 可跑 |
| **项目实验** | 1–2 gNB + 30–60 UE + 平台 + 60 车 + pcap | 8–12 | 16–24 GB | 100 GB | ⚠️ 需把 WSL 提到 20–24 GB |
| **批量/多 UE** | 100–1000 UE + 多 gNB + 多实例 | 16–24 | 32–64 GB | 500 GB | ❌ 不建议 WSL |

宿主有 34.2 GB，WSL 设 20–24 GB 可行，但要给 Windows 留 8–10 GB。建议：

```ini

memory=24GB

swap=8GB
```

然后 `wsl --shutdown` 重启。若 Windows 还要跑浏览器/Office，降到 20 GB 更稳。

#### 组件预算

| 组件 | CPU | RAM | 说明 |
|---|---|---|---|
| Open5GS 9 个 NF | 0.5–1 核空闲，2–4 核负载 | 0.3–0.8 GB | AMF/SMF/UPF/NRF/UDM/AUSF/PCF/NEF/BSF |
| MongoDB | 0.2–0.5 核 | 0.3–0.8 GB | 用户签约数据 |
| UERANSIM gNB | 0.5–1 核 | 50–100 MB | SCTP 连 AMF |
| UERANSIM UE × 60 | 1–3 核 | 0.6–1.2 GB | **1 个 UE 1 个进程** |
| V2X 平台 | 1–2 核 | 2–4 GB | 取决于 Kafka/DB/API |
| SUMO + Python | 1–2 核 | 0.3–0.5 GB | 现有仿真 |
| pcap/tshark | 0.5–1 核 | 0.2–0.5 GB | 磁盘 I/O |
| OS/cache | 1 核 | 2–4 GB | |
| **合计** | **5–10 核** | **4–8 GB** | 建议 8–12 核 / 16–24 GB 留余量 |

#### 网络与磁盘

- **网络**：CAM 级别 600 pps，1 GbE 足够；不需要 10 GbE，除非做高速用户面镜像。
- **pcap 体积**：60 UE × 10 Hz × 300 B ≈ 180 KB/s；60 s 约 11 MB，加头/信令约 **30–50 MB/场景**。1000 场景约 30–50 GB，磁盘够。
- **如果跑视频/远控用户面**：100 Mbps × 60 s ≈ 750 MB/场景；1000 场景 750 GB，接近磁盘上限，必须抽样或压缩。
- **WSL NAT 限制**：Win10 下局域网不能直接访问 WSL 内部 5GC；`netsh portproxy` 主要解决 TCP，NGAP/SCTP、GTP-U/UDP 不适合对外暴露。**外部检测器最好跑在 WSL 内，或离线读 pcap**；Win10 没有 mirrored networking。

#### 硬件结论

- 15.5 GB：只能做 5–10 UE 的最小验证；60 UE + 平台会很紧。
- 20–24 GB：60 UE + 平台 + SUMO + pcap 可跑，这是推荐配置。
- 1000 UE：UERANSIM 进程模型吃不消，需要 32–64 GB、16–24 核、Linux 宿主；本机不适合，批量仍应走语义层。

#### 软件栈

**推荐：Docker Compose + 源码 UERANSIM。**

- Open5GS + MongoDB 用 Docker：镜像约 1–2 GB，配置可版本化；UPF 容器需要 `--cap-add NET_ADMIN`、挂载 `/dev/net/tun`，必要时 `--privileged`。
- UERANSIM 源码编译：需要 `libsctp-dev`、`libssl-dev`、`cmake`、`g++`、`make`；编译本身可在用户态，但装依赖要 root。
- 不建议 rootless Podman：UPF 的 TUN/NET_ADMIN 容易受限。
- 不建议一上来源码编译 Open5GS：Ubuntu 26.04 太新，依赖和包版本容易踩坑；Docker 更稳。

#### 配置与订阅数据

这是最容易卡住的地方：

- Open5GS：PLMN、TAC、S-NSSAI、DNN、UE IP 池（如 `10.45.0.0/16`）、AMF/SMF/UPF 地址。
- UERANSIM gNB：PLMN、TAC、NCI、AMF IP、N2/N3 地址。
- UERANSIM UE：SUPI/IMSI、K、OPc、DNN、S-NSSAI。
- MongoDB 里的 subscriber 必须和 UE 配置**逐项一致**，否则注册被拒，日志很难一眼看出。
- 建议用 `open5gs-dbctl` 或 CSV 脚本批量导入，不依赖 WebUI。
- NEF 在 Open5GS 里支持有限；A8 这类 NEF 攻击可能需要自研 API/mock。

#### 平台

- 如果“真实平台”是课题现有平台：需要它的部署包、运行时（Java/Node/Python）、数据库、消息总线、TLS/证书、API key；这部分工作量取决于对方交付物。
- 如果只是“真实 API 形态”：用 FastAPI + MQTT + Postgres/SQLite 做一个轻量平台，成本低很多，也足够做 A9 的 token/云控注入。
- 真实平台的鉴权/租户/订阅模型如果不清楚，A8/A9 会变成“假攻击”。

#### 外部检测系统的网络位置

- 外部系统在 **WSL 内**：最容易，直接读 `lo`/`ogstun`/`eth0` 的 pcap 或事件流。
- 外部系统在 **Windows 宿主**：可以访问 WSL IP，但 Win10 NAT 下局域网机器不能直接访问；TCP API 可 portproxy，SCTP/GTP-U 不适合。
- 外部系统在 **局域网另一台 PC**：需要把 pcap 导出后离线分析，或改用 Linux 桥接 VM；Win10 WSL2 没有 mirrored networking，不能直接镜像 WSL 内部流量。
- 如果对方是黑盒设备、只给镜像口，方案2 在 Win10 WSL 下很难满足，建议改用独立 Linux 宿主 + 桥接网卡。

#### 我能做 vs 你需要做

**我能做（用户态）：**

- Docker Compose、Open5GS/UERANSIM 配置、subscriber CSV；
- root 安装脚本、网络 setup/cleanup 脚本；
- SUMO/仿真与 5GC 的编排、时间对齐、真值映射；
- pcap 后处理、日志/metrics 适配、外部检测器接口；
- 攻击剧本（A5/A7/A9 等）和测试。

**需要你执行（root/系统层）：**

- `apt install`、Docker 安装、内核模块、`/dev/net/tun`、`sysctl`、`iptables`；
- MongoDB/Open5GS 服务启动；
- `.wslconfig` 修改和 WSL 重启；
- Windows 防火墙/portproxy；
- 外部平台/检测器的部署包和账号。

> 我所在 shell 是受限命名空间：`sudo` 不可用，也看不到 `/dev/net/tun`；普通 WSL 终端里 `sudo` 可用且能看到设备。因此 5GC/UE 的启动需要你在普通终端执行，或放开权限。

### 6.4 工程复杂度对比方案1

#### 方案1基线

方案1 = 语义级 core/platform：

- 约 1,500 LOC，单进程，Python；
- 4–6 人周；
- 确定性、18 进程并行、无 root；
- 覆盖 5–6 个跨层剧本，事件级/链级真值。

#### 复杂度对比

| 维度 | 方案1 | 方案2 | 倍数 |
|---|---|---|---|
| 代码量 | ~1,500 LOC | 3,000–5,000 LOC | **2–3×** |
| 进程/服务 | 1 | 10–20+ | **10×** |
| 环境/权限 | 无 root | root + 内核 + 网络 | 从 0 到 1 |
| 攻击实现 | 进程内 Hook | 进程/配置/网络/API/补丁 | **3–5×** |
| 数据对齐 | 同进程时钟 | 多进程日志 + pcap + 指标 | **3–5×** |
| 复现性 | 同种子逐字节一致 | 抖动、状态清理、端口冲突 | **3–5×** |
| 批量 | 18 并行 | 1–4 并行 | **慢 5–10×** |
| 维护 | 低 | 高（版本/依赖/网络） | **5×** |

**总体：代码量 2–3 倍，集成/联调/运维 4–6 倍，进度风险 3–5 倍。**

如果包含真实 V2X 平台：代码 3–5 倍，集成/运维 6–10 倍。  
如果还要 PC5 协议级：再乘 2–3 倍，且 Open5GS/UERANSIM 不覆盖 PC5，需要 ns-3/Veins/OAI 等另一套工具链，**不建议本期做**。

#### 人周估算

| 工作 | 方案1 | 方案2（核心网） | 方案2（含平台） |
|---|---:|---:|---:|
| 环境/root/网络 | 0 | 1–2 周 | 1–2 周 |
| 5GC/UE 集成 | 0 | 2–3 周 | 2–3 周 |
| 数据/标签/pcap | 0.5 周 | 2–3 周 | 2–4 周 |
| 攻击剧本 | 1–2 周 | 3–5 周 | 3–5 周 |
| 平台 | 0.5–1 周 | 1–2 周 | 2–4 周 |
| 测试/文档 | 1 周 | 2–3 周 | 2–3 周 |
| **合计** | **4–6 人周** | **12–20 人周** | **16–24 人周** |

这是“能跑通、能出数据”的估算，不含协议一致性认证和现网调优。

#### 各攻击在方案2下的难度

| 攻击 | 难度 | 原因 |
|---|---|---|
| A5 信令风暴 | 中 | 多 UE 进程/脚本；AMF 过载；资源控制 |
| A6 QoS/切片 | 中高 | Open5GS 策略/DB/配置；可能需要 API/补丁 |
| A7 UPF/N6 | 中 | 路由/iptables/TUN；需要 root |
| A8 NEF | 高 | Open5GS NEF 支持有限；需 mock/自研 |
| A9 平台越权 | 中 | 取决于平台 API/鉴权 |
| A10 组合隐蔽 | 高 | 多进程时序、链级关联、日志对齐 |

#### 为什么不是线性增长

方案2 的难点不在“写代码”，而在：

- **环境不可复现**：端口、TUN、SCTP、MongoDB、Docker 网络，任何一处状态残留都会让下一次运行失败；
- **时间不同步**：Open5GS/UERANSIM/SUMO/平台四套时钟，pcap 与真值对不齐；
- **攻击面实现方式不同**：语义层改一个字段，方案2 可能要改配置、iptables、数据库或打补丁；
- **批量能力下降**：语义层 18 进程，方案2 1–4 个实例就到顶；
- **协议一致性**：pcap 能“解出来”不等于“状态机合法”，DPI 过不了很常见。

### 6.5 Go / No-Go

- 拿不到 root/无法改 WSL 配置 → **方案2 不可行**；
- 外部系统能接 JSON/Kafka/NetFlow → **方案1 足够**；
- 外部系统必须 pcap + DPI → **方案2 或协议投影**；
- 必须覆盖 PC5 → **方案2 不够**，要另加 PC5 工具链；
- 必须 1000 UE/批量 → **方案2 不适合**，用语义层；
- 必须 5G-A 的 NWDAF/RedCap/NTN/ISAC → **Open5GS 不够**，要定制/商业核心网。

## 7 建议实施路线

### 7.1 分阶段

| 阶段 | 内容 | 产出 | 验收 |
|---|---|---|---|
| **P0（约 1 周）** | 修 truth 一致性；gNB 从“雷达传感器”升级为 RAN 节点；加 `trace_id`/`chain_id`；加链级评估；加 truth-domain 静态测试 | 测试/报表 | 每个 `domain` 都有对应流记录；A1–A4 回归不变 |
| **P1（约 2–3 周）** | 语义级 core/platform + 图 + Web；改造 A1/A4；新增 A5/A7/A9 | 新层/新剧本 | 新攻击≥99%；正常≤1%；P99≤100 ms；数据量 +<30% |
| **P2（约 1–2 周）** | A6/A8/A10 + `defense.action` + 恢复 | 防御闭环 | 隔离/阻断/恢复时延；附带损伤可测 |
| **P3（可选）** | Open5GS/UERANSIM 点验 | 协议样本 | 只做点验，不进主循环 |

### 7.2 验收硬约束

1. `truth.domains` 必须等于本次运行实际写入的流域；
2. 每个新剧本至少覆盖 3 个域，且有先后因果；
3. 正常集必须包含新层的合法波动，否则不报误检率；
4. 现有 A1–A4 的 500+500 结果作为回归基线，加层后不得劣化；
5. 链级指标单独报告：节点/边 recall/precision、阶段顺序、根因 top-1、链完整度；
6. 时延分两条口径：快路径（≤100 ms）和链确认（单列）。

### 7.3 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| 新层正常行为未覆盖 | 误检率 >1% | 加注册风暴、切换乒乓、切片重配等难负样本 |
| 链级关联凑窗 | 100 ms 时延超 | 快路径 + 链确认双口径；流式关联 |
| truth 与数据不一致 | 评审/复现风险 | truth-domain 静态测试；A4 先修 |
| schema 不兼容 | 外部消费失败 | 升 `isacsim.record/2`，保留 v1 读取 |
| 图边被截断 | 核心网边丢失 | 分层图/top-k 采样 |
| 5GC 环境不可复现 | 结果不可复现 | Docker Compose + 固定版本 + 清理脚本 |
| PC5 不被覆盖 | “全协议”名不副实 | 明确 sidecar 边界；PC5 另立项目 |
